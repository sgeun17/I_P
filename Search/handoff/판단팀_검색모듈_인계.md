## 이 모듈이 제공하는 것

증적의 청크 텍스트를 받아 **그 문서와 관련된 ISMS-P 인증기준 후보 Top-K(기본 5개)를 반환**합니다. 로컬 BGE-M3로 의미를 벡터화하고 ChromaDB에 저장된 101개 인증기준을 검색합니다. 청크별 Top-K도 검색 근거 확인용으로 제공합니다.

결과에는 원문 청크·위치 정보, 후보 순위·유사도, 후보 기준의 요구사항이 포함됩니다. 최종 매핑, 적정성 판단, confidence, 판단 근거 및 인용문 작성은 이 모듈의 반환값에 포함되지 않습니다.

```text
증적 1개에 대한 청크 목록
 → 청크마다 BGE-M3(text만 사용)
 → ChromaDB의 인증기준 101개와 각 청크의 유사도 계산
 → 같은 통제항목의 청크별 점수 중 최댓값을 문서 점수로 사용
 → 중복 없는 문서 Top-K + 근거 청크 + 원문/위치 + 요구사항 반환
```

## Python에서 연결

Search가 모듈 검색 경로에 있는 환경에서:

```python
from chunk_retriever import retrieve

result = retrieve(preprocessed_document, top_k=5)
if not result["success"]:
    handle_error(result["error"])
else:
    evidence_chunks = result["evidence_chunks"]
    candidate_controls = result["candidate_controls"]
    document_candidates = result["retrieval"]["candidates"]  # 판단팀이 먼저 볼 문서 Top-K
    per_chunk_candidates = result["retrieval"]["chunk_results"]  # 청크별 상세 확인
    # 위 값을 판단 모듈의 입력 규격에 맞춰 전달
```

`retrieve()`는 Search의 가상환경으로 별도 프로세스를 실행합니다. 호출자 작업 폴더를 바꾸지 않으며 한 요청의 모든 청크를 같은 모델 로딩으로 처리합니다. 호출할 때마다 모델을 로드하므로 상시 서비스의 성능 최적화는 후속입니다. 기본 제한시간은 600초입니다. 현재 제공 인터페이스는 **Python 함수와 JSON 파일/명령행**이며 HTTP 검색 서버는 포함하지 않습니다.

## 입력 규격

증적 하나와 버전 하나를 담은 객체입니다. 서로 다른 문서·버전을 한 요청에 섞지 않습니다.

| 문서 필드 | 의미 |
|---|---|
| evidence_id | 비어 있지 않은 문자열. 저장 모듈 값 `"000001"` 등을 그대로 유지 |
| version | 1 이상의 정수 |
| source_file | 원래 파일명 |
| file_type | pdf/docx/xlsx/pptx/txt/csv |
| chunks | 문서 순서대로 정렬된 청크 목록. 1~5000개 |

각 청크는 다음 필드를 포함합니다.

| 청크 필드 | 처리 규칙 |
|---|---|
| chunk_id | 중복 없는 식별자. 검색 결과와 원문을 연결하는 키. 검색 모듈은 재발급하지 않음 |
| evidence_id, version, source_file, file_type | 문서 정보와 일치 |
| chunk_index | 0부터 연속 번호 |
| text | 검색 대상 원문. 공백·줄바꿈을 포함해 출력에 그대로 보존. 빈 본문은 오류 |
| heading | 제목 또는 null. 이번 버전에서는 검색 문장에 별도로 추가하지 않음 |
| chunk_type | text/table |
| page_start, page_end | PDF 페이지 / PPTX 슬라이드 / XLSX 시트. DOCX/TXT/CSV는 null |
| block_orders | 원본 블록 번호 목록 |
| source | parser/ocr |

800글자는 입력팀의 현재 청킹 설정입니다. 검색 모듈은 글자 수가 아니라 모델 토큰 한도를 확인하며 초과하면 조용히 잘라내지 않고 오류를 반환합니다. 오류가 하나라도 있으면 요청 전체가 실패하고 부분 결과는 반환하지 않습니다.

## 출력에서 읽어야 할 곳

| 출력 필드 | 판단팀 사용법 |
|---|---|
| success | 먼저 확인. false이면 error를 처리하고 판단을 실행하지 않음 |
| evidence_id, version | 대상 증적 식별 |
| evidence_chunks | 입력 청크 원문·위치 정보. 실제 인용에 사용할 자료 |
| retrieval.candidates[] | 문서 전체 Top-K. rank/control_id/control_name/similarity_score/best_chunk_id/matched_chunk_ids |
| retrieval.chunk_results[] | chunk_id별 Top-K. 문서 후보 순위와 구별해서 상세 확인 |
| candidate_controls[] | 문서 Top-K와 같은 ID·순서의 K개 요구사항. requirement 포함 |
| retrieval.candidates[].best_chunk_id | 문서 점수를 결정한 최고 유사도 청크. 동점이면 먼저 나온 청크 |
| candidate_controls[].matched_chunk_ids | 이 후보가 청크별 Top-K에도 포함된 청크 ID 목록. 적합성 판정이나 인용 검증 결과가 아님 |
| warnings | 입력팀 현재 형식에 대한 임시 호환 변환 기록. 기본 모드는 [] |
| index | 검색에 사용한 KB 해시·벡터 캐시 식별자·컬렉션 |

후보 점수는 **cosine similarity = 1 − cosine distance**, 범위는 -1~1이며 높은 순으로 rank 1부터 부여합니다. 점수는 소수점 6자리까지 반환합니다. 원 거리 동점은 control_id 문자열 오름차순으로 정렬합니다. 반올림 때문에 같은 점수로 보이는 후보가 생길 수 있습니다.

**유사도는 정답 확률이나 판단 모델의 confidence가 아닙니다.** 현재 관련성 임계값을 두지 않아 무관한 청크에도 K개 후보가 반환됩니다. 후보에 포함됐다는 이유만으로 매핑을 확정하면 안 됩니다.

`top_k=5`이면 **문서 전체 후보 5개**와 청크별 상세 후보 각 5개가 나옵니다. 같은 통제항목이 여러 청크에 나와도 문서 후보에는 한 번만 등장합니다. `candidate_controls`도 문서 후보 5개만 담습니다. 지원 범위는 K=1~101입니다.

예를 들어 2.5.1의 청크별 유사도가 0.7, 0.4, 0.6이면 문서 점수는 0.7이고 첫 청크가 best_chunk_id입니다. 모든 통제항목을 이 방법으로 집계한 뒤 상위 K개를 선택합니다. `retrieval.aggregation=max_chunk_similarity`로 규칙을 표시합니다. 이 규칙은 한 부분의 관련성이 문서 전체 후보에 반영되도록 하지만, 청크가 많은 문서나 짧은 일반 문구가 순위에 영향을 줄 수 있습니다. 여러 번 언급됐다고 가점을 주지는 않습니다.

0.1에서 전환하는 소비자는 `retrieval.results`를 `retrieval.chunk_results`로 변경하고, 판단 입력 후보는 `retrieval.candidates`에서 읽어야 합니다. 이전의 전체 청크 합집합 대신 문서 Top-K만 전달됩니다. 원문 인용은 후보의 청크 ID로 evidence_chunks를 찾아 수행합니다. 페이지는 시작/끝 범위를 유지합니다. 루트의 초기 설계 문서보다 이 폴더의 실행 예제와 JSON Schema를 현재 구현 규격으로 확인해 주세요.

## 오류 예시와 대응

| code | 대응 |
|---|---|
| INVALID_INPUT / EMPTY_TEXT | ID·자료형·파일명·페이지·빈 본문·청크 중복 확인 |
| PREPROCESSING_FAILED | 파서 오류 해결 후 다시 전달 |
| INPUT_TOO_LONG | 해당 본문을 더 짧게 청킹 |
| INDEX_MISSING / INDEX_MISMATCH | 현재 KB와 모델로 전체 재색인 |
| TIMEOUT | 청크 수·실행 환경 확인, 필요 시 호출 제한시간 조정 |
| INVALID_INPUT_FILE | 파일 경로 또는 JSON 문법 확인 |
| SEARCH_FAILED / WORKER_FAILED / ENVIRONMENT_ERROR | 설치 환경·DB·실행 오류 확인 |

CLI는 성공 종료코드 0, 실패 1을 반환합니다. 출력 파일을 지정하면 실패 결과도 같은 파일에 기록하므로 항상 success를 확인하세요. 파일 읽기 실패 등과 별개로 출력 경로에 쓰기 권한이 없으면 파일 생성 자체가 실패할 수 있습니다.

## 인수 확인과 남은 합의

- 기계 검사 규격: `schemas/chunk_input.schema.json`, `schemas/chunk_output.schema.json`.
- 실행 결과: `reports/chunk_integration_result.md`.
- 실제 DOCX 샘플의 청크→문서 Top-5→JSON 연결 검사와 합성 검토 샘플 20건의 검색을 각각 실행했습니다. 샘플 결과는 `reports/review_evaluation.md`, 예상 정답 초안은 `tests/review_cases.json`입니다. 운영 정답률 확정 자료가 아닙니다.
- 합의할 사항: 증적 ID 표현, 문서 점수의 최대 유사도 집계 방식, 페이지 범위 필드, 오류·호환 경고 처리, 입력팀 수정 후 기본 모드 전환.
- 남은 검증: 정답 초안의 사람 검수 및 별도 실제 증적 평가, KB 최종 검수와 버전 고정, 업로드 서버와 판단 모듈의 실제 통합 실행.
