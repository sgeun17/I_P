# 판단팀 코드 확인 및 검색 연결 결과

2026-09-24. 새로 추가된 `I_P/판단`의 모델·서비스·검증기·정책·스키마·테스트를 확인했습니다. 검색팀에 변환 모듈을 추가했고 판단팀·입력팀 원본 파일은 변경하지 않았습니다.

## 해결한 연결 차이

판단팀 문서의 “문서별 후보 합치기 미구현 / requirement 미전달”은 검색팀 9/23 구현 이전 상태를 설명합니다. 현재는 문서 전체 Top-5를 최대 청크 유사도로 집계하고 요구사항도 반환합니다. 다만 두 팀의 JSON 포장이 달라 그대로 전달하면 판단팀 입력 검사에서 거부됩니다.

| 검색 결과 | 판단팀 MappingInput | 변환 처리 |
|---|---|---|
| evidence_id, version | 동일 | 값 그대로 유지 |
| evidence_chunks | chunks | 청크 본문·ID·페이지·출처 그대로 유지 |
| retrieval.candidates의 rank/ID/명칭/점수 | candidate_controls의 같은 필드 | 문서 Top-5 순서·점수 보존 |
| candidate_controls의 requirement | 후보 객체의 requirement | control_id를 확인해 결합 |
| matched_chunk_ids | source_chunk_ids | 실제 청크별 Top-K에 포함된 청크 목록 |
| retrieval.top_k | top_k | 값 그대로 유지 |
| index.kb_sha256 | kb_sha256 | 판단팀 KB 해시·101개 ID·명칭과 일치 확인 |

`judgment_adapter.to_mapping_input()`이 이 변환을 수행합니다. 실패 검색, 잘못된 순위·청크 참조·KB 해시·요구사항, 판단팀 규격에 맞지 않는 청크는 오류로 거부합니다. 본문을 자르거나 ID를 재발급하지 않습니다.

원본 검색 JSON도 함께 보관해야 합니다. MappingInput에 없는 warnings, best_chunk_id, 청크별 상세 점수, embedding_cache_key는 원본에 남습니다. model_revision은 원본 검색 출력에 없으므로 추정해 넣지 않았습니다. 판단팀에서는 선택 필드입니다. 재현용 버전 정보를 완성하려면 실제 임베딩 revision을 검색 출력에 기록하는 규격 보완이 필요합니다.

Search 폴더에서:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-handoff.txt
.\.venv\Scripts\python.exe -X utf8 judgment_adapter.py --input reports/chunk_search_result.json --output examples/judgment_mapping_input.json
```

성공 종료코드는 0이며 출력은 MappingInput 객체 자체입니다. 실패 종료코드는 1이고 출력 파일에는 `success=false` 오류 객체를 기록합니다. 이전 성공 파일을 잘못 읽지 않도록 실패 결과로 갱신합니다. 호출자는 종료코드를 확인하고 실패 시 판단을 실행하지 않아야 합니다.

Python 연결 예제(검색팀·판단팀 모듈이 각각 import 가능한 실행 환경):

```python
from chunk_retriever import retrieve
from judgment_adapter import to_mapping_input
from models import MappingInput

search_result = retrieve(preprocessed_document, top_k=5)
payload = to_mapping_input(search_result)  # 실패 시 MappingAdapterError. 호출자가 처리
mapping_input = MappingInput.model_validate(payload)
# 이후 LLM 하네스에 mapping_input을 전달
# raw_response를 받은 뒤 service.build_result(raw_response, mapping_input, versions) 호출
```

현재 `service.build_result()`는 LLM을 호출하지 않습니다. LLM의 원본 응답을 받아 파싱·검증·검토·결과 조립을 하는 함수입니다. 설치된 판단팀 파일에서 실제 모델 호출부·프롬프트 실행부는 확인되지 않았습니다.

## 실행한 검사

- 판단팀 기존 테스트 **265개 통과**.
- 검색팀 및 변환 단위 테스트 **19개 통과**.
- 실제 검색 출력 **26건**(오늘 파일 시험 성공 6건 + 어제 개발 샘플 20건)을 판단팀의 실제 Pydantic MappingInput으로 검증.
- 전처리 실패 출력 **2건**의 변환 거부 확인.
- 실제 판단팀 build_result·Validator·Review 코드에 **고정 시험 응답 6종**을 넣어 실행: 단일 매핑, 복수 매핑, NO_MATCH, 허위 인용, 깨진 JSON, 호출 실패.
- 원문 청크·순위·검색 점수·요구사항 전달 및 최종 결과의 검색 점수 일치 확인.

**LLM 호출은 0회입니다.** 시험용 응답과 confidence=0.9는 검사 상수이며 자동 판단 결과·정답률로 사용하면 안 됩니다. 단일 매핑도 실제 검색 1·2위 점수 차이가 작으면 R202로 검토에 들어갑니다. 허위 인용은 processing_status=COMPLETED여도 validation.passed=false이고 REVIEW_REQUIRED이므로, 처리 완료만 보고 자동 확정하면 안 됩니다.

## 판단팀에 확인 요청할 부분

1. **임계값 YAML이 실행 코드에 연결되지 않음.** `configs/thresholds.yaml`과 문서는 파일 수정으로 정책을 조정한다고 설명하지만 `src/review_policy.py`는 `DEFAULT_THRESHOLDS = Thresholds()`를 사용합니다. 현재 파일 값과 코드 기본값은 같아 이번 결과에는 차이가 없지만, YAML만 바꿔도 실행값이 바뀌는 구조는 아닙니다. YAML 로더 연결 또는 문서 정정이 필요합니다. 호출 제한·재시도 설정은 LLM 하네스 연결 때 별도 확인해야 합니다.
2. **800자·ID 규칙 차이.** 판단팀은 청크 text 800자 이하 및 `{evidence_id}_v{version}_c{index:04d}`를 강제합니다. 검색 코어는 모델 토큰 한도와 ID 고유성을 검사하므로 검색에 성공해도 판단 입력에서 거부될 수 있습니다. 이번 변환부는 더 엄격한 판단팀 규칙을 확인하며 내용·ID를 임의 변경하지 않습니다. 장문의 표 청크 등은 입력팀과 정책 합의가 필요합니다.
3. **문서의 청킹 겹침 설명이 실제 코드와 다름.** 판단팀 `docs/output_schema_v0.3.md`는 긴 문단 분할에 겹침이 없다고 설명하지만 입력팀 `chunker.py`는 긴 문단을 나눌 때 100자 겹침을 적용합니다. 짧은 문단 묶음 경계에는 적용하지 않습니다. 인용 중복 처리의 전제를 실제 구현에 맞춰 확인해야 합니다.
4. **README의 검색팀 미해결 항목 갱신.** 문서 단위 Top-5와 requirement 전달은 구현됐으며 이제 변환 예제도 제공됩니다. 이 변환 형식과 source_chunk_ids 의미를 승인할지 확인해 주세요.
5. **실제 LLM 하네스 연결.** 고정 응답 검사를 통과한 뒤 실제 LLM 응답으로 정상·무관·복수 항목 증적을 실행해야 합니다. 프롬프트·모델 버전은 실제 값을 기록하고, 호출 실패·재시도·Timeout 정책도 함께 연결해야 합니다.

이 요청서는 코드와 실행 결과에 근거한 협업 확인 사항입니다. 판단팀 규격·임계값·원본 코드는 임의로 수정하지 않았습니다.
