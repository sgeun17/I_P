# 9/26 Phase 2 기준 초안

오늘 작성한 것은 **우선 항목 후보 5개, 공통 체크리스트 구조, 3개 항목의 질문 30개**다. 채은·유빈 및 연동팀의 검토를 위한 초안이며, 운영 코드가 읽는 확정 KB는 아니다.

## 먼저 볼 파일

- [체크리스트 검토본](checklist_review.md): 사람이 읽기 편한 질문·근거 예시 표.
- [체크리스트 JSON](checklist_draft.json): 동일 질문과 문항별 충족·미충족·판단불가 조건.
- [합성 검토 사례 9개](review_examples.json): 질문 3개에 대해 MET·NOT_MET·UNKNOWN의 차이를 설명하는 사례. 실제 실행 결과나 승인된 정답은 아니다.
- [구조 검사 결과](validation_report.json): ID·기준 연결·필드·예제 참조 검사 결과. 내용의 타당성이나 모델 성능 승인을 의미하지 않는다.

기준: 프로젝트 루트 `WBS.xlsx`, 시트 `WBS`. 담당자 C21:C26은 채은·유빈, 오늘 날짜 L2는 2026-09-26이다.

## 공통 구조 제안

### 체크리스트 파일

| 필드 | 형태·작성 규칙 |
|---|---|
| draft_version | 초안 버전. 현재 phase2-checklist-draft-2026-09-26 |
| status / approved | DRAFT_FOR_TEAM_REVIEW / false. 팀 승인 전 유지 |
| source | 기준 KB 경로·SHA-256·작성 근거. 현재 파일의 requirement를 사용 |
| priority_candidates | 우선 후보와 선정 이유. 체크리스트 작성 완료 목록과 구분 |
| proposed_result_values | MET, NOT_MET, UNKNOWN 제안. 실행 API의 확정 ENUM이 아님 |
| controls | 통제항목 ID·명칭·현재 KB 요구사항 원문과 items |

### 검사 질문 하나

| 필드 | 형태·작성 규칙 |
|---|---|
| item_id | 문자열. 임시 규칙은 control_id-Q두자리, 예: 2.5.1-Q01. 확정 후에는 순서 변경만으로 ID를 재사용하지 않음 |
| control_id | 기존 Phase 1 ID와 동일. 임의로 새 통제 ID를 만들지 않음 |
| source_clause | 현재 KB requirement에서 가져온 해당 문구. 원문 문서 쪽수는 아직 대조 전 |
| question | 확인할 조건 하나를 질문 형태로 작성. 복수 조건이 남았는지 사람 검토 필요 |
| check_kind | procedure(절차 수립), implementation(이행), record(기록) 구분 제안 |
| critical / critical_status | 현재 null / UNDECIDED. false로 간주하거나 등급 계산에 사용하지 않음 |
| evidence_rule.candidate_evidence | 확인에 도움이 되는 자료 예시. 해당 파일명을 제출해야 한다는 필수 목록이 아님 |
| evidence_rule.met | 해당 조건의 이행·존재를 직접 뒷받침하는 근거가 있을 때의 초안 기준 |
| evidence_rule.not_met | 적용되는 조건을 지키지 않았다는 사실이 확인될 때의 초안 기준 |
| evidence_rule.unknown | 근거 부재·범위 불명·판독 불가·상충 등으로 결론을 내릴 수 없는 경우 |
| evidence_rule.citation_required_for | MET·NOT_MET에는 판단을 뒷받침하는 원문 인용을 요구하는 제안 |
| evidence_rule.scope_rule | 확인한 대상·기간에만 판단 적용. 일부 사례를 조직 전체로 확대하지 않음 |
| review_status | 현재 DRAFT. 승인 전 상태를 문항별로 표시 |

이 JSON은 **검사 기준 데이터**다. 증적별 판정 결과, confidence, overall_result를 저장하는 형식은 아니다. Phase 2 입력·출력 API와 결과 스키마는 WBS의 인터페이스 담당 팀과 별도로 맞춰야 한다.

## 질문 작성·판정 기준 초안

1. 현재 KB의 requirement에 근거한 질문만 작성한다. keyword나 evidence_examples에 있는 표현을 새로운 의무로 자동 승격하지 않는다. 예를 들어 백업 주기·권한 검토 주기·파기 기한을 임의의 숫자로 고정하지 않는다.
2. 절차가 있다는 것과 절차대로 운영했다는 것을 구분한다. 백업 성공 로그만으로 보관기간·소산·적시 복구까지 충족했다고 보지 않는다.
3. 관련성은 충족 여부와 다르다. 계정 관련 문서여도 이 체크리스트 대부분의 질문은 근거 부족으로 UNKNOWN일 수 있다.
4. MET은 해당 질문을 뒷받침하는 충분한 근거가 있을 때 제안한다. 합성 검토 사례의 짧은 문장은 필드 의미를 설명하기 위한 것이며 실제 운영 판정에 충분하다는 뜻이 아니다.
5. NOT_MET은 적용되는 조건을 지키지 않았다는 직접 근거가 있을 때 제안한다. 제출된 청크에서 언급이 없다는 이유만으로 미충족 처리하지 않는다.
6. 적용 대상·기간·주기·기준일이 없거나 근거가 불충분하면 UNKNOWN을 제안한다. 사건이 발생하지 않은 경우의 적용 제외 여부도 아직 미합의다. UNKNOWN을 충족이나 미충족으로 자동 변환하지 않는다.
7. 여러 청크·문서가 있어야 답할 수 있는 질문이 있다. 필요한 원문과 출처를 보존하고, 근거가 상충하면 단순 최고 점수로 하나를 고르지 않는다. 최신성·상충 해소 규칙은 추가 합의한다.
8. 점수만으로 문항을 판정하거나 종합 등급을 계산하지 않는다. critical, 항목 집계, UNKNOWN 처리, 적용 제외 처리의 합의가 먼저 필요하다.

## 현재 팀 자료에서 확인한 점과 연결할 때의 조건

판단팀 `src/prompts.py`는 Phase 1의 역할을 후보 통제항목과 증적의 관련성 판단으로 한정하고 충족·미충족 판정을 금지한다. 따라서 이 체크리스트는 현재 Phase 1 프롬프트에 바로 넣을 자료가 아니라, Phase 2 판단을 준비하기 위한 기준이다.

판단팀 `docs/human_review_policy_v0.1.md`는 검토 대기·반려 결과의 Phase 2 전달을 제한한다. 실제 Phase 2 연결에서는 확정된 매핑 및 유효성·처리 상태를 함께 확인하는 전달 조건을 담당 팀과 맞춰야 한다. NO_MATCH를 통제항목 미충족으로 바꾸지 않는다.

지금 논의 중인 청크 크기·문서 Top-K 최대 점수 집계 방식은 이번 작업에서 변경하지 않았다. 관련·무관·부분 관련 문서의 실제 청킹과 최종 관련성 판단을 먼저 검증한 뒤 조정 방향을 결정할 수 있다.

## 검토 때 정할 것

| 검토 대상 | 제안할 질문 |
|---|---|
| 채은·유빈 | 이 5개 후보로 시작해도 되는지? 빈도·중요도 또는 확보된 실제 증적을 근거로 바꿀 항목이 있는지? |
| 기준 작성 담당 | 공식 점검 원문과 대조했을 때 질문에 누락·추가 해석이 있는지? critical을 어떤 기준으로 정할지? |
| 판단 담당 | 한 통제항목의 여러 증적·청크를 함께 볼 수 있는지? 근거 부재는 UNKNOWN, 명시적 미이행은 NOT_MET으로 구분하는 방향이 맞는지? |
| 인터페이스 담당 | Phase 2가 받는 확정 매핑, 증적 범위·기간·기준일, 인용 정보를 어디에 담을지? |
| 판정 담당 | critical 미정, UNKNOWN, 해당 사건 없음 또는 적용 제외를 종합 결과에 어떻게 반영할지? |

체크리스트 작성 자체의 세부 의미를 확정하기 위한 질문이다. 다른 팀이 해당 기능을 아직 구현하지 않았다고 단정하는 목록은 아니다.

## 다음 작업

검토 후 우선 범위와 공통 필드를 정하고, 질문 중복·누락을 수정한다. 이후 실제 증적과 예상 결과를 붙여 문항별 판정 가능성을 확인한다. 그 다음 버전 관리 KB 적재와 Phase 1 ID 동기화를 진행한다. 공식 원문 전체 대조·최신 법규 검토·LLM 평가·통합 실행은 이번 초안 작성에 포함하지 않았다.
