# 입력팀 파싱·청킹 코드 분석

분석일: 2026-09-23. `I_P/입력`의 현재 파일 기준입니다. 입력팀 원본 코드는 수정하지 않았습니다. 업로드 서버·MySQL은 실행하지 않았으며, 제공된 DOCX 파일의 파싱→청킹을 직접 호출했습니다. PDF·XLSX·PPTX·TXT·CSV 파서는 구조를 읽었고 모든 형식의 실제 파일 시험을 수행한 것은 아닙니다.

## 현재 구성

| 파일 | 역할 | 현재 연결 상태 |
|---|---|---|
| `입력/main.py` | 업로드 검사, 원본 저장 호출, 목록·조회·삭제, 분석 요청 UI | 분석 시작 함수는 queued 응답만 반환. 실제 파서·청킹 호출 없음 |
| `입력/database/evidence_store.py` | 원본 경로·증적 ID·버전·파일 해시·처리 상태 관리 | 메타데이터/원본 관리. 청크 저장 기능은 확인되지 않음 |
| `입력/*_test/*_parser.py`, `docx-test/extract_docx.py` | 파일에서 제목·본문·표를 블록 목록으로 추출 | 개별 함수/실행 코드 존재 |
| `입력/chunker.py` | 파서 블록을 크기 제한에 맞게 글·표 청크로 분할 | 개별 함수 존재. import 경로와 공통 형식 조정 필요 |
| `입력/chunk/table_chunker.py` | 표의 행을 ‘열 이름: 값’ 텍스트로 변환·분할 | table_chunks는 연결됨. 이어진 표 머리글 보완 함수는 미연결 |
| `입력/chunk/chunk_format.py` | 공통 청크 키, ID, 검증 함수 정의 | make_chunk_id만 사용. finalize_chunks·validate_chunks는 make_chunks에서 호출하지 않음 |

## 데이터 흐름

의도한 흐름: 원본 파일 → 형식별 파서 → `blocks` → `make_chunks(parsed, evidence_id, version)` → 청크 목록 → 검색 모듈.

현재는 각 함수가 존재하는 상태이며 업로드→파싱→청킹→검색이 자동으로 연결되어 있지 않습니다. `make_chunks`의 반환값은 Python의 `list[dict]`입니다. JSON 파일을 자동 저장하거나 `{"evidence_id": ..., "chunks": [...]}` 형태로 감싸는 코드는 없습니다. 이번 분석에서 반환값을 별도로 JSON 파일로 저장했습니다.

파서 반환값의 기본 키: `source_file`, `file_type`, `page_count`, `blocks`, `errors`.
각 블록의 키: `order`, `block_type`(heading/paragraph/table), `level`, `page`, `text`, `table`.
표는 파서 단계에서 `text`가 비고 `table.rows`에 2차원 배열이 들어가며, 청킹 단계에서 검색 가능한 문장으로 바뀝니다.

## 실제 DOCX 실행 결과

- 입력: `입력/docx-test/test1.docx`
- 임시 실행 인자: `evidence_id=1`, `version=1` (DB에서 발급받은 실증적 번호가 아님)
- 파서 오류: 없음
- 파서 블록: 4개 (제목 → 본문 → 표 → 본문)
- 청크: 3개 (글 → 표 → 글)
- 공통 규격 검증: 3개 모두 `source_file` 누락으로 실패
- 일반 import는 `ModuleNotFoundError: No module named 'chunk_links'`로 실패하므로, 이번 시험에 한해 입력 폴더와 chunk 폴더를 모듈 검색 경로에 추가해 호출했습니다.

| 청크 ID | 유형 | 내용 |
|---|---|---|
| 000001_v1_c0000 | text | 제1장 총칙 + 제1조 목적 |
| 000001_v1_c0001 | table | 구분/내용, 접근통제, 로그관리 표의 텍스트 |
| 000001_v1_c0002 | text | 제2조 적용범위 |

두 번째 청크의 실제 text:

```text
구분: 내용
접근통제: 사용자 계정은 승인 후 발급한다
로그관리: 접속기록은 1년간 보관한다
```

이 텍스트는 그대로 BGE-M3의 입력이 될 수 있습니다. 제목을 추가할지는 검색 입력 규칙으로 정하면 됩니다. ID·파일명·페이지 등은 벡터 숫자에만 의존하지 말고 결과와 함께 보존해야 합니다.

## 청킹 규칙

- 기본 최대 크기는 **800글자**이며 토큰 수가 아닙니다.
- 짧은 제목·본문 블록은 800글자 이내로 모읍니다. 새 제목·표를 만나면 기존 묶음을 마칩니다.
- 단일 블록이 800글자를 넘으면 문장 끝·줄바꿈·공백 부근으로 나누고, 기본 100글자를 겹칩니다.
- 서로 다른 짧은 본문 블록을 모으다가 800글자를 넘어 나누는 경계에는 현재 overlap이 적용되지 않습니다. 450글자 문단 2개를 넣은 시험에서 450/450글자로 나뉘었습니다.
- 900글자짜리 단일 블록은 800/200글자로 나뉘어 100글자가 겹칩니다.
- 글 청크와 표 청크는 섞지 않습니다. 표는 가능한 행 단위로 나누고 겹침은 없습니다.
- PPTX/XLSX는 슬라이드/시트가 바뀌면 글 묶음을 나눕니다. PDF 글 묶음은 페이지를 걸칠 수 있어 시작·끝 페이지를 기록합니다.
- PDF=페이지, PPTX=슬라이드, XLSX=시트 번호입니다. DOCX/TXT/CSV는 페이지 값이 null입니다.
- 파서의 errors가 있으면 make_chunks는 빈 목록을 돌려주며 오류 내용을 별도 전달하지 않습니다. 호출부에서 파서 오류를 보존해야 합니다.

## 연결 전에 해결할 사항

1. **모듈 경로**: `chunker.py:1`은 하위 chunk 폴더의 chunk_links를 최상위 모듈처럼 import합니다. 일반 실행에서 실패함을 확인했습니다. 패키지 import 또는 명확한 실행 진입점이 필요합니다.
2. **파일명/출처 필드**: `chunker.py:105`는 source에 파일명을 넣습니다. 표 조각의 source=parser가 뒤에서 덮어써져 글은 경로, 표는 parser가 됩니다. 공통 규격은 source_file=파일명, source=parser/ocr입니다. source_file을 시험용 사본에 추가해 검사하면 글 2개의 source 오류도 확인됩니다.
3. **증적 ID 자료형**: 저장 모듈의 `_next_evidence_id`는 문자열 `"000001"`을 만들지만, make_chunk_id는 양의 정수만 허용합니다. 저장 ID를 그대로 전달하면 ValueError가 발생했습니다. 공통 ID 규칙을 결정한 후 연결부에 명시적으로 반영해야 합니다.
4. **공통 형식 완성·검증 미연결**: make_chunks가 직접 청크를 조립해 finalize_chunks를 사용하지 않습니다. 전달 전에 공통 형식으로 조립하고 validate_chunks를 통과시키는 과정이 필요합니다.
5. **페이지를 넘긴 표 머리글 보완 미연결**: fill_continued_headers 함수가 있지만 make_chunks가 호출하지 않습니다. 합성 2페이지 표 시험에서 다음 페이지 첫 데이터 행이 머리글로 오인됐습니다. 기존 보완 함수를 먼저 적용하면 같은 시험은 정상 변환됩니다. 이 보완 함수 자체는 휴리스틱이므로 다양한 실제 표에 대한 검증은 별도입니다.
6. **원본 파일명 보존**: DOCX는 전달 경로 전체를 source_file로 쓰지만 다른 파서는 경로의 파일명만 씁니다. 저장 후 이름이 000001_v1.docx처럼 바뀌면 원래 파일명은 파서만으로 복구할 수 없습니다. 저장 메타데이터의 file_name을 함께 전달해야 합니다.

PDF에 이미 들어 있는 텍스트를 추출하는 코드는 있으나, 현재 확인한 디렉토리에 이미지 OCR을 실행하는 파이프라인은 없습니다. PDF 전체에서 텍스트를 얻지 못하면 empty_document 등이 나오며 검색 입력으로 자동 전환되지 않습니다.

## 검색 연결 방향

입력팀의 공통 청크 형식을 기준으로 위 차이를 먼저 맞추고, 원본 파일 하나를 실제 파싱·청킹해 규격 검사를 통과시킵니다. 이후 각 청크의 text를 BGE-M3로 벡터화하고, 101개 KB ChromaDB를 검색하면 됩니다. 청크 ID·증적 ID·버전·페이지 범위를 유지해 반환하면 어떤 원문의 검색 결과인지 추적할 수 있습니다.

이번 산출물:
- `docx_parsed.json`: 실제 파서 반환값
- `docx_chunks_actual.json`: 실제 청킹 반환값 (형식 불일치도 그대로 보존)
- `diagnostics.json`: ID·형식 검사와 합성 표/겹침 시험 결과

입력팀 소스 수정, 검색 연결 구현, 서버/MySQL 연결 검증은 이번 분석에 포함하지 않았습니다.
