# KB 해시 불일치 확인 — 2026-10-02

## 수정 완료: 판단팀 동기화 안내

검색팀의 KB 식별 계산을 `kb_identity.py`의 **`sha256-crlf-v1`**로 통일했다. KB를 읽은 바이트에서 `CRLF → LF → CRLF` 순으로 개행만 통일한 다음 SHA-256을 계산한다. JSON 재직렬화나 내용 수정, 해시 불일치 무시 처리는 하지 않는다. `controls.json` 저장·checkout은 LF로 고정했다.

**공유 `kb_sha256`은 기존 `6421a840c5fd84d1f4ea7e3e60c8df95aab8be8d71cf1e437fb67729a9e803be`를 유지한다.** 파일 원본 바이트 해시 `d69396…`는 별도 값이며 새 규칙의 KB 식별자로 넣으면 안 된다. 기존 판단팀 인덱스·샘플과 기존 정상 검색 인덱스의 공유 해시는 그대로 사용한다. KB 내용이 실제로 바뀌면 계속 차단한다.

판단팀에서 할 일:

1. 검색팀 수정본 전체를 동기화한다. 특히 새 `kb_identity.py`와 `judgment_adapter.py`, `chunk_retriever.py`, `chroma_index.py`를 함께 받는다. 어댑터 한 파일만 복사하면 새 모듈이 누락된다.
2. 판단 인덱스와 샘플의 `kb_sha256`이 위 `6421a840…803be`인지 확인한다. 현재 확인한 판단팀 자료는 이미 일치하므로 값을 변경할 필요가 없다. KB 해시를 별도 계산하는 코드가 있다면 같은 공유 함수를 사용한다.
3. 실행 중인 검색·판단 프로세스를 재시작하고 기존 연결 테스트를 실행한다. 이미 다른 값으로 생성한 색인·출력은 수정된 검색 코드로 다시 생성한다. 기존 정상 `6421a840…` 색인은 이번 개행 변경만으로 재임베딩할 필요가 없다.

Phase2 기준의 KB 참조 확인에도 동일한 함수를 적용했다. 기준 JSON·카탈로그와 판단팀 기존 코드는 수정하지 않았다. 체크리스트·PDF·보고서 등 다른 파일의 원본 바이트 무결성 검사는 유지한다.

검증: 검색 55개, Phase2 기준 98개, 판단팀 어댑터 연결 계약 9개 테스트 통과. LF/CRLF 모두 기존 샘플로 입력 변환이 가능하고, 실제 KB 변경·잘못된 해시는 거부된다. 실제 LLM 호출은 필요하지 않아 실행하지 않았다.

아래는 **수정 전 진단 기록**이다. 당시 원본 바이트 해시와 현재 공유 KB 식별 규칙을 구분해서 읽는다.

## 확인 결과

현재 PC에서는 검색 KB, 판단팀 control_index와 샘플 4개의 KB 해시가 일치한다. 실제 장애가 발생한 팀원의 파일·오류 전문은 아직 받지 않았다.

| 대상 | SHA-256 |
|---|---|
| 현재 Windows `controls.json` 원본 바이트(CRLF) | `6421a840c5fd84d1f4ea7e3e60c8df95aab8be8d71cf1e437fb67729a9e803be` |
| 같은 파일의 줄바꿈만 LF로 변환 | `d69396f252b9990a4ffc7a4773dd852af87a635cdfbb6539d1113dc8b80bd177` |
| Git HEAD의 `phase1_검색/controls.json` 바이트 | `d69396f252b9990a4ffc7a4773dd852af87a635cdfbb6539d1113dc8b80bd177` |
| 판단팀 `data/control_index.json`의 `kb_sha256` | `6421a840c5fd84d1f4ea7e3e60c8df95aab8be8d71cf1e437fb67729a9e803be` |
| 판단팀 `samples/`의 JSON 4개 | 모두 `6421a840…803be` |

Git HEAD와 로컬 KB를 JSON으로 읽은 결과는 동일하다. 로컬 파일에서 CRLF 2,748개를 LF로 바꾼 바이트는 Git HEAD와 완전히 일치한다. 판단팀 인덱스의 101개 ID·명칭도 현재 KB와 일치한다. 따라서 이 두 해시의 차이는 기준 내용의 차이가 아니라 줄바꿈 차이다. `control_index.json` 파일 자체의 해시와 비교한 것이 아니라 그 안에 기록된 KB 해시를 비교했다.

## 차단 위치와 재현

- [검색팀 어댑터](../judgment_adapter.py): 검색 결과의 `index.kb_sha256`, 실제 `controls.json` 바이트 해시, 판단팀 인덱스에 기록된 해시가 모두 같아야 통과한다.
- [판단팀 어댑터](../../phase1_판단/src/retrieval_adapter.py): 검색 결과의 KB 해시와 로드한 `DEFAULT_INDEX.kb_sha256`이 다르면 거부한다.

기존 [검색 샘플](../examples/docx_output.json)을 두 어댑터에 전달하면 모두 통과했다. 복사한 샘플의 KB 해시만 위 LF 해시로 바꿔 전달하면 두 어댑터 모두 해시 불일치로 거부했다. 메모리에서 재현했으며 원본 KB·샘플·판단팀 코드는 수정하지 않았다. 실제 검색 재실행이나 LLM 호출은 하지 않았다.

팀원 측 해시가 `d69396f2…bd177`이면 이 줄바꿈 차이와 정확히 부합한다. 다른 해시라면 같은 버전인지, 추가 편집·인코딩 차이가 있는지 실제 파일을 대조해야 한다.

## 담당과 수정 방향

1. 검색팀이 배포할 KB의 바이트 형식과 해시 계산 규칙을 먼저 정한다. 현재는 파싱한 JSON 내용이 아니라 파일 원본 바이트의 SHA-256을 사용하므로 Git 줄바꿈 변환도 영향을 준다.
2. 판단팀은 합의한 기준 KB로 `control_index.json`의 ID·명칭·해시와 현재 실행용 샘플을 재생성한다. 단순히 오류를 피하려고 임의의 해시를 복사하거나 검사를 제거하지 않는다.
3. 기준 해시를 바꾸면 검색 색인·캐시·검색 출력 샘플도 같은 기준으로 재생성 또는 검증해야 한다. Phase2의 기존 54문항·현재 700문항 JSON도 `source.sha256`으로 현재 KB를 참조하므로 버전·참조 해시 변경 영향을 함께 확인해야 한다. 과거 실행 기록의 해시는 당시 값을 보존한다.
4. 양쪽 어댑터 연결 검사를 수행하고, 인덱스를 이미 로드한 판단 프로세스를 다시 시작해 확인한다.

원본 바이트 해시를 유지한다면 KB 파일의 줄바꿈·인코딩과 Git 저장/배포 방식을 고정해야 한다. 정규화한 JSON의 해시로 바꿀 경우에는 검색·판단·Phase2에서 동일한 정규화 규칙과 버전을 사용하도록 별도로 합의해야 한다. 이번 확인에서는 어느 방식도 임의로 적용하지 않았다.

판단팀 단독의 코드 수정 문제로 단정하기보다, 검색팀이 KB 배포 기준을 고정하고 판단팀이 파생 인덱스·샘플을 동기화하는 공동 변경으로 처리하는 것이 맞다.
