# 일반 검색 호출의 BGE-M3 모델 재사용 — 2026-09-27

이전 `retrieve()`는 매 요청마다 검색 프로세스를 실행하고 BGE-M3를 로드했다. 현재는 첫 유효 요청에서 검색 프로세스·모델·ChromaDB 연결을 초기화하고 같은 호출 프로그램의 후속 요청에서 재사용한다. 함수 인자와 `retriever-0.2` 성공·실패 JSON은 유지된다.

## 사용법

```python
from chunk_retriever import retrieve, close_retriever

try:
    first = retrieve(first_document, top_k=5)
    second = retrieve(second_document, top_k=5)  # 같은 검색 프로세스·모델 재사용
finally:
    close_retriever()  # 상시 서버는 개별 요청 종료가 아니라 서버 종료 시 호출
```

기존 `retrieve(document)` 호출도 자동으로 재사용된다. 모델을 사용할 때까지 프로세스를 띄우지 않으며, 호출 프로그램 종료 시 자동 정리한다. `close_retriever()`는 진행 중인 요청이 끝난 뒤 모델을 해제하고, 이후 요청은 새 프로세스로 시작한다.

## 수명·오류 처리

| 상황 | 처리 |
|---|---|
| 같은 프로그램의 연속 요청 | 검색 프로세스·모델·DB 연결 재사용 |
| 동시 요청 | 잠금으로 한 건씩 처리하고 요청 ID로 응답 연결 확인 |
| 전처리 실패·잘못된 입력 | 모델 초기화 전에 거부. 기존 정상 프로세스 유지 |
| 검색 처리 대기 중 제한시간 초과 | TIMEOUT 반환. 다른 요청이 사용하는 프로세스 유지 |
| 입력 전송·검색·응답 중 제한시간 초과 | TIMEOUT 반환 후 해당 프로세스 폐기. 다음 요청에서 재시작 |
| 검색 프로세스 종료·잘못된 응답·통신 실패 | WORKER_FAILED 반환 후 정리. 다음 요청에서 재시작 |
| 실제 검색 오류 | 기존 SEARCH_FAILED·INDEX_MISMATCH 등 실패 JSON 반환. 호출자가 success를 먼저 확인 |
| 프로그램 종료 또는 close_retriever() | 자신이 실행한 프로세스·파이프·모델 메모리 정리 |

기본 `timeout=600`초이며 처리 대기시간도 포함한다. `timeout=None`은 시간 제한 없이 기다리고 양수가 아닌 값은 INVALID_INPUT이다. 늦은 응답은 다음 요청의 응답으로 사용하지 않는다. stderr의 모델 로딩 안내는 별도로 읽어 출력 JSON에 섞이지 않게 한다.

KB·모델·색인을 교체할 때는 요청을 중단하고 `close_retriever()`로 정리한 후 재색인하고 다시 요청한다. 실행 중 KB가 바뀌면 기존 해시 검사가 INDEX_MISMATCH를 반환한다. 재색인 중 검색하지 않는 기존 운영 규칙은 유지한다.

## 변경 파일과 적용 범위

- `chunk_retriever.py`: 공개 retrieve 경로를 재사용 클라이언트로 연결, 내부 연속 요청 처리 루프와 종료 함수 추가.
- `worker_client.py`: 프로세스 수명·동시 호출 직렬화·요청 제한시간·파이프 통신·오류 정리 구현.
- `tests/test_worker_reuse.py`, `tests/verify_model_reuse.py`: 프로세스 오류와 실제 모델 재사용 확인 도구 추가.
- 검색팀 README·기존 인계 문서·이 보고서: 호출 방법과 검증 결과 갱신.

검색·집계 알고리즘, KB, 입력팀·판단팀 코드, Phase2 및 저장소 루트 문서는 변경하지 않았다. 이전 검수용 스냅샷은 당시 버전으로 보존하며 현재 실행 코드 해시는 이번 보고서에 기록했다. 커밋·푸시는 하지 않았다.

재사용은 호출 프로그램 단위다. 별도 서버 프로세스는 각각 모델을 로드하며, 명령행 명령을 매번 다시 시작하면 모델도 다시 로드한다. 계속 실행 중인 서버에서 `retrieve()`를 반복 호출해야 효과가 유지된다. HTTP 검색 서버나 실제 업로드 서버 통합은 이번 변경에 포함하지 않는다.
