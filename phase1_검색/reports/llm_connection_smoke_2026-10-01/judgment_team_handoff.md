# 실제 Ollama 연결 검증 (2026-10-01)

개발 PC에서 SSH 터널로 GPU 서버의 Ollama에 접속하고 기존 Phase1 판단 코드를 실제 실행했다. 서버 연결은 성공했으며, 아래 판단·검증 문제는 판단팀 검토가 필요하다. 판단팀의 기존 코드 수정은 착수 후 중단했고, 이번에 적용했던 검증기·테스트 변경은 모두 원복했다. 남긴 작업은 실행 결과와 이 전달 문서의 추가다.

## 실행 환경과 범위

- Ollama: `0.35.0`
- 모델: `qwen3:14b`, `14.8B`, `Q4_K_M`
- 모델 digest: `bdbd181c33f2ed1b31c972991882db3cf4d192569092138a7d29e973cd9debe8`
- 호출 주소: `http://127.0.0.1:11435/v1/chat/completions`
- 연결: 개발 PC `127.0.0.1:11435` → 사용자 SSH 터널 → 서버 `127.0.0.1:11434`
- 설정: temperature=0, thinking=false (`reasoning_effort=none`), stream=false, max_tokens=4096, timeout=60초
- `/api/ps`에서 context_length=4096, 모델 메모리 size와 size_vram이 같은 값으로 관측됐다.
- 프롬프트: `phase1_mapping_v0.5`, 규칙: `mapping_rules_v0.7`, 골든셋: `goldenset_v0.1`
- 기존 합성 사례 3개를 원본 입력과 요구사항 추가 입력으로 각각 한 번 실행했다. 총 6회 호출이며 서로 다른 사례는 3개다.
- 실제 Retriever를 실행한 평가나 Phase2 충족·미충족 판단 평가는 아니다. 입력의 후보 순위·검색 점수는 기존 합성 fixture 값이다.

연결 성공·형식 통과·인용 존재와 의미상 정답 일치는 별개의 결과다. 특히 추가 입력의 MULTI는 매핑 정답과 일치하지만 검증기가 정상 업무 설명을 차단했다. 원본 입력의 후보 15개에는 requirement가 모두 없고, 추가 입력에서는 기존 마스터의 requirement를 동일 control_id로 연결했다. 정답·증적·후보 목록은 바꾸지 않았다. 입력 조건별 한 번의 관측이므로 요구사항 추가의 효과나 전체 정확도로 일반화할 수 없다.

## J-LLM-01 — 업무 설명을 적정성 판정으로 오인한 E505

**우선 확인: 판단팀 검증기. 미수정 상태.**

위치: [validators.py](../../../phase1_판단/src/validators.py), `ADEQUACY_PATTERNS`의 `부?적정(하|합|함|성)` 및 `detect_adequacy_judgment()`.

추가 입력의 `G-MULTI-01` 응답은 “정보보호담당자가 반기 1회 전체 사용자의 접근권한 적정성을 검토하고 결과를 기록한다”는 원문의 업무를 설명한다. 현재 검증기는 `적정성`이라는 단어 때문에 `candidate_decisions.reason`과 `mapped_controls.reason`에서 E505를 각각 한 번 발생시킨다. 이어서 R102 검토 사유가 추가된다.

모델이 해당 증적을 충족·미충족으로 판정한 문장은 아니다. 단어만으로 업무 설명과 적정성 결론을 구분하지 못하는 오탐으로 판단했다. 중립적인 검토 활동 설명과 실제 “적합하다/통제항목을 충족한다” 결론을 구분하도록 검토가 필요하다. 정상 설명 뒤에 실제 판정이 붙거나 `부적정성`이 나온 경우에도 기존 차단 기능은 유지해야 한다. 제안 수정은 적용하지 않았으며 수정 후 검증 결과도 없다.

## J-LLM-02 — 계정 삭제 사례의 관련성·PRIMARY 불일치

**우선 확인: 판단팀 프롬프트·관련성 판단 정책. 미수정 상태.**

`G-SINGLE-01` 원문에는 퇴직 당일 계정 비활성화, 관리자 승인, 계정 삭제, 관리대장 기록이 명시돼 있다. 현재 골든 정답은 `2.5.1 사용자 계정 관리 / PRIMARY` 하나다.

| 입력 조건 | 실제 모델 선택 |
| --- | --- |
| 원본 | `2.2.5 퇴직 및 직무변경 관리 / PRIMARY`, `2.5.1 사용자 계정 관리 / RELATED` |
| 요구사항 추가 | `2.5.6 접근권한 검토 / PRIMARY`, `2.2.5 퇴직 및 직무변경 관리 / RELATED`; `2.5.1`은 NOT_RELATED |

추가 입력에서 모델은 계정 삭제가 명시됐는데도 사용자 등록·보안책임 등의 내용이 없다는 이유로 `2.5.1`을 제외했다. 또 삭제 이력 기록을 권한 “점검”까지 수행한 것으로 설명했지만, 원문에 권한 검토·점검 활동은 없다. 인용 문자열 자체는 원문에 존재한다. 따라서 현재 인용 검사는 의미상의 관련성 오류를 잡지 못한다.

“통제항목 요구사항 중 관련 활동이 나타나는가”와 “요구사항 전체를 충족하는가”를 혼동했을 가능성이 있다. 이는 응답을 바탕으로 한 추론이며, 원인은 아직 확정하지 않았다. 이 구분과 문서의 주된 목적에 따른 PRIMARY 선택을 함께 검토해야 한다.

## J-LLM-03 — 기존 정답의 매핑 경계 검토

[controls.json](../../../phase1_검색/controls.json)의 `2.2.5` 요구사항에도 퇴직 시 계정·접근권한 회수가 들어 있다. 따라서 `2.2.5` 추가 선택을 허위 인용이나 무조건 무관한 항목이라고 단정하면 안 된다. 현재 정답과 불일치했다는 것은 확인됐다.

계정 삭제 요청서에 `2.2.5 RELATED`도 허용할지, PRIMARY는 어떤 원칙으로 정할지 담당자 검수가 필요하다. 평가 수치를 높이기 위해 기존 골든 정답을 임의로 바꾸지 않았다.

## J-LLM-04 — 골든셋과 실제 전달 입력의 차이

[goldenset.json](../../../phase1_판단/tests/fixtures/goldenset.json)의 원본 smoke 입력에는 후보 requirement가 없다. 현재 [retrieval_adapter.py](../../../phase1_판단/src/retrieval_adapter.py)는 실제 검색 결과의 requirement가 비어 있으면 오류를 낸다. [prompts.py](../../../phase1_판단/src/prompts.py)는 전달받은 requirement를 모델 입력에 포함한다.

따라서 원본 골든셋 smoke 결과만으로 실제 검색→판단 전달 조건을 검증했다고 보기 어렵다. 요구사항을 추가한 입력을 원본과 별도로 저장해 이 차이를 확인했다. 평가 입력을 실제 계약에 맞추는 작업과 골든 정답 검수는 구분해서 진행해야 한다.

## J-LLM-05 — 출력 필드 생략과 reason 경고

프롬프트는 인용이 없는 후보도 `citations: []`를 출력하도록 요구하지만, 원본 NO_MATCH의 5개 후보와 추가 입력 SINGLE·NO_MATCH의 총 8개 후보에서 필드를 생략했다. Pydantic 기본값이 빈 배열로 보완해 현재 형식 검사에서는 허용된다. 이를 허용 계약으로 둘지 엄격히 요구할지는 판단팀 결정이 필요하다.

추가 입력 SINGLE에서는 reason에 원문을 길게 다시 인용해 E507 경고가 4개 발생했다. 현재 경고는 검증 실패·재시도의 원인이 아니다. 이 문제는 매핑 정확도 및 허위 인용 여부와 구분해 확인해야 한다.

## 해결된 접속 문제

처음에는 SSH 창에 `connect failed: Connection refused`가 나오고 서버 자체의 `/api/version`도 연결되지 않았다. 사용자 실행으로 Ollama 서비스를 시작한 뒤 버전·모델 조회와 실제 6회 호출이 성공했다. 현재 연결을 쓰려면 사용자 SSH 터널 창을 열어둬야 한다.

실제 문서 정확도, 29건 전체 성능, 반복 실행 안정성, 실검색 품질과 운영 처리량은 이번에 측정하지 않았다. 런타임 context_length는 4096으로 관측했으며, 정확한 프롬프트 토큰 수와 잘림 여부도 확인하지 않았다. Phase2의 700문항 초안을 LLM으로 판정하는 실행 경로는 이번 검증 범위에 포함되지 않는다.
