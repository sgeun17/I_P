# Human Review 정책 v0.1

작성: 판단팀 · 2026-09-21
상태: **초안. 임계값은 전부 임시값**

---

## 1. 무조건 검토

임계값과 무관하게 사람에게 보낸다. 기계가 판단할 수 없는 것들이다.

| 사유 코드 | 상황 |
|---|---|
| `R101` | JSON 파싱 실패 |
| `R102` | 스키마 위반 (필수 필드 누락, 잘못된 Enum, confidence 범위 초과) |
| `R103` | 통제항목 ID 오류 (KB에 없음, 후보 밖 생성, 이름 불일치, 중복) |
| `R104` | Citation 검증 실패 (없는 청크, 원문에 없는 문장, 페이지 불일치) |
| `R105` | 매핑됐는데 Citation이 없음 |
| `R106` | `PRIMARY` 개수가 1이 아님 |
| `R107` | 후보 판단에 `UNCERTAIN`이 하나라도 있음 |
| `R108` | LLM 호출 재시도 실패 |
| `R109` | Prompt Injection 의심 |
| `R110` | 입력이 판단 불가 (청크 0개·후보 0개·후보 중복). **LLM을 부르지도 못했다** |

> **화면 담당에게 — `R107`이 붙은 `NO_MATCH`는 "관련 없음"이 아니다.**
> `match_status`에는 보류를 나타내는 값이 없어서, 후보가 전부 `UNCERTAIN`이어도
> 결과는 `NO_MATCH`로 나온다. `R107`이 있으면 **"판단 보류"**로 표시해야 한다.
> 그대로 "관련 통제항목 없음"이라고 띄우면 검토자가 오해한다.
> 규칙은 `mapping_rules_v0.7.md` 4.4에 있다.

## 2. 조건부 검토

임계값으로 판단한다. **`thresholds.yaml`에서만 바꾸고 코드는 건드리지 않는다.**

| 사유 코드 | 조건 | 임시값 |
|---|---|---|
| `R201` | 매핑된 항목의 `llm_confidence`가 낮음 | `< 0.70` |
| `R202` | 1위와 2위 후보의 검색 점수 차가 작음 | `< 0.01` |
| `R203` | 매핑된 통제항목이 너무 많음 | `> 3개` |
| `R204` | 결과가 `NO_MATCH` | 초기 ON |
| `R205` | 결과가 1:N 매핑 | 초기 ON |
| `R206` | 검색 점수는 높은데 전부 `NOT_RELATED` | 최고 점수 `>= 0.55` |
| `R207` | 인용된 청크가 OCR 산출물 (`source == "ocr"`) | 품질 점수가 없어 값 자체를 신호로 쓴다 |
| `R208` | 판단 근거가 된 청크 텍스트 **합계**가 짧음 | `< 30자` |

### 임계값을 지금 확정하지 않는 이유

0.70이라는 숫자에 근거가 없다. 골든셋 28건을 돌려보고
**검토율과 오탐율의 균형**을 보고 정해야 한다. 지금 고정하면 나중에 왜 그 값인지
아무도 설명하지 못한다.

`R204`, `R205`를 초기에 켜두는 이유는 `NO_MATCH`와 1:N이 가장 틀리기 쉬운 구간이라
초반에 사람 눈으로 패턴을 봐야 하기 때문이다.

> **2026-09-24 판단팀 결정: 켜고 시작한다.**
> 골든셋 29건 기준 켜면 24건(83%), 끄면 14건(48%)이 검토 대상이다.
> 정확도가 안정되면 `R204`(NO_MATCH)부터 끄고, 그다음 `R205`(1:N)를 본다.
> 근거와 측정 결과는 `goldenset_v0.1.md` 4.2 참고.

### 검토율 목표

초기에는 높아도 된다. 다만 **전체의 60%를 넘으면 도구의 의미가 없다.**
골든셋 평가에서 이 수치를 반드시 측정한다.

## 3. 상태

처리 상태와 검토 상태를 **반드시 분리한다.** 하나로 합치면
"LLM은 끝났는데 사람이 아직 안 봄" 같은 상태를 표현할 수 없다.

```
processing_status   PENDING → PROCESSING → COMPLETED / FAILED   (기계)
review_status       NOT_REQUIRED | PENDING → APPROVED / MODIFIED / REJECTED   (사람)
```

### 전이 규칙

| 현재 | 허용되는 다음 |
|---|---|
| `NOT_REQUIRED` | 없음 |
| `PENDING` | `APPROVED`, `MODIFIED`, `REJECTED` |
| `APPROVED` | 없음 |
| `MODIFIED` | 없음 |
| `REJECTED` | 없음 |

확정된 결과는 되돌리지 않는다. 다시 봐야 하면 **새 판단을 만들고 이전 것은 이력으로 남긴다.**
결과를 덮어쓰면 "언제 뭐가 바뀌었는지"를 잃는다.

### Phase 2로 넘어가는 조건

```
review.required == False                          → 전달
review.status in (APPROVED, MODIFIED)             → 전달
review.status in (PENDING, REJECTED)              → 전달하지 않음
```

`REJECTED`는 "이 매핑은 틀렸다"는 뜻이므로 Phase 2가 받으면 안 된다.

### MODIFIED 처리

사람이 고친 결과가 최종이다. 단, 원본을 지우지 않는다.

| 저장 항목 | 내용 |
|---|---|
| 원본 | LLM이 낸 결과 |
| 수정본 | 사람이 고친 결과 |
| 수정자·시각 | `reviewer_id`, `reviewed_at` |
| 메모 | `review_note` |

수정 이력은 **골든셋의 원천**이 된다. 사람이 고친 사례가 곧 정답 데이터다.
