# Phase2 Qwen3:14B 실제 호출 검수 — 2026-10-01

대표 3문항에 대해 충족·미충족·판단불가의 가상 사례 9건을 두 조건으로 실행했다. **실제 LLM 요청은 총 18회**다. 기본 조건에서는 판정 9건이 기대값과 일치했지만 충족 결과 2건에 잘못된 사유 코드가 붙었다. 비교 조건에서는 형식·사유·인용 검사가 전부 통과했으나 대상이 다른 자료를 근거로 미충족을 단정한 오판 1건이 발생했다.

실제 호출과 구조 검증의 첫 실행을 완료했다. 실제 조직 증적 검증, 전체 700문항 성능 평가, 사람 정답 검수와 운영 승인은 완료하지 않았다.

## 실행 범위와 조건

- 문항: `2.1.1-Q01`(절차), `2.4.1-Q02`(실행), `2.10.1-Q03`(기록). 각 문항에 MET/NOT_MET/UNKNOWN 사례 1건씩 사용했다.
- 자료: [기존 가상 사례 9건](../tests/fixtures/chapter2_review_cases.json). 기대 판정·기대 사유 코드는 AI 초안이며 사람 승인 정답이 아니다. 기대값과 설명은 모델 입력에서 제외했다.
- 기준: 전체 체크리스트 `phase2-checklist-chapter2-full-draft-2026-10-01-r3`와 전용 사유 카탈로그 `phase2-reason-codes-chapter2-full-draft-2026-10-01-r3`를 명시적으로 선택했다. 기본 54문항 카탈로그는 변경하지 않았다.
- 모델: Ollama `0.35.0`, `qwen3:14b`, 14.8B, `Q4_K_M`. 모델 digest는 두 실행에서 동일하다.
- 접속: 기존 SSH 터널의 `http://127.0.0.1:11435/v1` OpenAI 호환 API.
- 생성: temperature 0, thinking false, stream false, 출력 상한 1,024토큰, 요청 제한 60초, 허용 재시도 1회. 실제 재시도는 0회다.
- 출력: `ItemJudgment.model_json_schema()`를 제공해 문항 ID·통제항목 ID·판정·설명·사유 코드·인용을 받았다. 버전·증적 묶음 정보는 검수 실행기가 요청에서 연결했다.
- 검토 대상·기간: 가상 A시스템, 2026년 3분기. `applicable_basis`와 `effective_basis`는 미기재 상태로 유지하고 경고를 기록했다. 미확인 정보를 임의로 채우지 않았다.
- Phase1 확정 매핑은 가상 입력이다. 실제 검색·통제항목 매핑 성능을 측정하지 않았다.

기본 조건은 판단팀의 기존 프롬프트를 재사용하고 검수용 스키마·문맥을 연결했다. 비교 조건은 같은 입력 값에 **사유 사용 규칙 명시와 JSON 표시용 공백 축소**를 함께 적용했다. 둘을 동시에 바꿨으므로 개별 변경의 효과를 분리해 주장할 수 없다. 각 조건은 1회씩만 실행했다.

## 판단팀 전달사항

이번 작업에서는 판단팀의 기존 코드를 수정하지 않았다. 다음은 확인 결과와 보완 제안이며, 팀 코드에 적용된 수정 목록이 아니다.

| 구분 | 확인한 내용 | 보완·협의할 내용 |
|---|---|---|
| 실제 오류: 사유 계약 | [기존 프롬프트](../../phase2_판단/src/grounding_prompts.py)는 MET에서 빈 사유를 허용한다고 안내하지만, 검수 카탈로그는 MET에 다른 판정용 코드를 붙이면 거부한다. 기본 실행에서 2건 발생했다. | 프롬프트와 결과별 사유 검사 규칙을 맞추고, 사유 검사 실패도 재시도·검토 경로에 연결할지 협의. 현재 하네스 성공 9/9가 외부 검사 성공을 보장하지 않는다. |
| 실제 오류: 대상·결론 연결 | 비교 실행에서 다른 대상의 자료로 미충족을 확정했다. 기존 프롬프트의 대상 불명확 시 단정 금지 지시만으로는 방지되지 않았다. | 대상 불일치·미확인 자료를 회귀 사례로 유지하고, 직접 근거와 결론의 연결을 검토할 절차 보완. 문자열 인용 검사만으로 자동 확정하지 않기. |
| 모의 재현: JSON 중복 키 | [하네스의 `_parse_json`](../../phase2_판단/src/judgment_harness.py)은 일반 JSON 파싱으로 중복 키의 마지막 값을 채택한다. 모의 응답에 `result=UNKNOWN`과 `result=MET`을 중복 입력하면 MET으로 처리되어 하네스가 성공했다. | 중복 키를 원문 파싱 단계에서 거부하는 방식 검토. 검수 실행기는 별도 엄격 파서로 거부한다. **실제 18개 모델 응답에서 중복 키는 관찰되지 않았다.** |
| 실행 한계: 전체 토큰 예산 | 서버의 실제 `context_length`는 4,096이다. 기본 실행 3건의 서버 보고 `total_tokens`가 이를 넘었다. 정확한 Qwen 토크나이저 기반 호출 전 전체 예산 검사는 연결하지 않았다. | 시스템·사용자 입력, 스키마와 출력 여유를 포함한 예산 검사 및 서버 컨텍스트 설정 확인. 이 수치만으로 입력 잘림이나 오판 원인을 단정하지 않는다. |

[중복 키 모의 재현](phase2_llm_smoke_reason_rules_2026-10-01/duplicate_key_reproduction.json)은 `mock_only=true`, `llm_executed=false`다. 실제 LLM 오류 건수와 구분한다.

기본 실행의 서버 보고 입력 토큰은 3,766~3,922, 전체는 3,942~4,162였다. 비교 실행은 입력 3,397~3,555, 전체 3,583~3,798로 모두 4,096 이하였다. 비교 실행의 오판 사례는 전체 3,732토큰으로 보고됐으므로 컨텍스트 초과 때문에 발생했다고 주장하지 않는다. 모델 메타데이터의 지원 길이 40,960과 서버의 실제 실행 길이 4,096도 구분한다.

## 변경 범위와 다음 검증

이번 작업의 추가·수정은 `phase2_기준`의 검수 실행 도구, 결과 폴더, 이 보고서와 README 안내다. 실행 전후 해시로 체크리스트·사유 카탈로그·사례와 Phase1/Phase2 판단팀 소스가 유지된 것을 확인했다. 기존 Phase2 테스트 **97개 및 하위 검사 248개가 통과**했다.

다음 검증에는 실제 조직 자료와 대상·기간·적용 기준을 확인한 사람 정답이 필요하다. 우선 대상 불일치 오판과 사유 계약을 판단팀에 전달하고 회귀 검증 범위를 정한다. 예외 처리와 critical, 사유 코드 의미의 팀 확정은 보류 상태를 유지한다. 이번 가상 사례 결과를 전체 700문항 정확도나 실제 증적 검증 완료로 표시하지 않는다.
