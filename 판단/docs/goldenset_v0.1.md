## 4. 이번에 찾아낸 것

### 4.1 `R202` 임계값 0.03은 노이즈였다

1·2위 점수 차가 작으면 검토로 보내는 조건이다. 값을 훑어봤다.

| `narrow_score_gap` | R202 발동 | **단독으로 검토를 결정** | 전체 검토율 |
|---:|---:|---:|---:|
| 0.05 | 19건 | 1건 | 83% |
| 0.03 | 17건 | 1건 | 83% |
| 0.02 | 9건 | 1건 | 83% |
| **0.01** | **2건** | **1건** | **83%** |
| 0.005 | 1건 | 1건 | 83% |
| 0 (끔) | 0건 | — | 79% |

0.03이면 17건에서 걸리는데 **그중 16건은 이미 다른 이유로 검토행이었다.**
검토 결정은 하나도 바꾸지 못하면서 사유 목록만 길어진다.
검토 화면에서 "왜 검토인지"가 흐려지는 게 실제 손해다.

→ **0.01로 낮췄다.** 검토율은 그대로고 사유가 선명해진다.

### 4.2 검토율을 결정하는 것은 `R204`와 `R205`다

| 설정 | 검토율 |
|---|---:|
| 현재 (`thresholds_v0.3`) | **83%** |
| `NO_MATCH`를 검토로 안 보냄 | 66% |
| 1:N을 검토로 안 보냄 | 66% |
| 둘 다 끔 | **48%** |
| 둘 다 끔 + 점수차 조건도 끔 | 41% |

**"1:N·NO_MATCH를 초기에 전부 검토로 보낼지"가 검토율을 35%p 좌우한다.**
팀이 정해야 할 항목 중 영향이 가장 크다.

자동 확정되는 것은 **단일 매핑 5건뿐**이다. 나머지는 전부 사람이 본다.

83%는 `human_review_policy_v0.1.md`에 적어둔 상한 60%를 넘는다.
초기에는 의도한 것이지만, **정확도가 안정되면 `R204`부터 끄는 것이 순서**다.
`NO_MATCH`가 9건 중 5건에서 단독 결정자이기 때문이다.

### 4.3 짧은 청크 검사가 동작하지 않고 있었다

`R208`(청크가 너무 짧음)이 **인용된 청크만** 검사하고 있었다.
그런데 `NO_MATCH`면 인용이 없으므로 검사가 아예 돌지 않았다.
"표지만 있는 문서"처럼 **근거가 부실해서 판단을 못 한 경우를 놓치는** 구멍이었다.

고친 규칙:

```
인용이 있으면  → 인용된 청크를 검사
인용이 없으면  → 증적 전체를 검사
길이는 청크 하나가 아니라 전체 합계로 잰다
```

합계로 재는 이유는, 긴 문서에 짧은 청크 하나가 섞였다고 검토로 보내면 과민해지기 때문이다.

## 5. 아직 확정 못 한 것

### 임계값은 여전히 임시다 — 점수가 가짜이기 때문

골든셋의 `similarity_score`는 **사람이 지어낸 값이다.**
검색팀 실측 1건(1·2위 차 0.0553)에 맞춰 분포를 흉내 냈을 뿐이다.

> **검색팀에 요청할 것**
> 골든셋 29건의 증적 본문으로 실제 Retriever를 돌려 점수를 뽑아주세요.
> 그 점수로 바꿔 넣으면 임계값을 근거 있게 정할 수 있습니다.

`low_confidence`(0.70)는 더 나쁘다. `llm_confidence`는 LLM이 매기는 값이라
**실제 모델을 붙이기 전에는 분포조차 알 수 없다.**

### 1:N 상한 3개는 지금 정답 분포와 맞는다

정답 개수 분포는 0개 9건, 1개 9건, 2개 4건, 3개 1건이다.
**4개 이상인 사례는 없다.** 다만 23건(ideal)은 표본이 작다.
실제 증적을 넣어보고 4개짜리가 나오면 상한을 올린다.

## 6. 케이스를 추가할 때

- 증적 본문은 **합성으로** 쓴다. 실제 문서 금지
- `control_id`는 반드시 KB에 있는 것을 쓴다 (생성기가 검사한다)
- 정답은 **후보 목록 안에** 있어야 한다. 밖에 있으면 검색 Recall 문제이지 판단 문제가 아니다
- 애매한 사례는 억지로 정답을 정하지 말고 `uncertain_ids`에 넣는다
- 왜 이 사례가 필요한지 `note`에 남긴다. 나중에 값을 바꿀 때 근거가 된다
