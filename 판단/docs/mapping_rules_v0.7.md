## 1. 결과 구조

두 단으로 나눈다.

| 층 | 필드 | 값 |
|---|---|---|
| 결과 전체 | `match_status` | `MATCHED` / `NO_MATCH` |
| 통제항목 하나 | `relation` | `PRIMARY` / `RELATED` |

1:1인지 1:N인지는 **저장하지 않는다.** `mapped_controls` 배열 길이를 보면 알 수 있고,
따로 저장하면 배열과 어긋난 값이 생길 수 있다. 화면에 "1:N"으로 표시할 일이 있으면
그때 계산해서 보여준다.

```
len(mapped_controls) == 1  →  1:1
len(mapped_controls) >= 2  →  1:N
match_status == NO_MATCH   →  매핑 없음
```

## 2. 후보별 판단값

Top-K 후보 **전부**에 대해 하나씩 판단을 남긴다. 고른 것만 남기면 오답 분석이 불가능하다.

| 값 | 기준 |
|---|---|
| `RELATED` | 증적 원문에 해당 통제항목의 대상 활동이 **직접** 나타난다. 인용할 문장이 있다 |
| `NOT_RELATED` | 관련 내용이 없다. 키워드만 겹치는 경우도 여기에 해당한다 |
| `UNCERTAIN` | 관련 있어 보이나 원문 근거가 불충분하다. **무조건 Human Review로 간다** |

`UNCERTAIN`을 넣는 이유는, 이게 없으면 모델이 애매한 걸 전부 `RELATED`나 `NOT_RELATED`로
밀어버려서 오류 유형을 구분할 수 없기 때문이다.
다만 모델이 애매하면 전부 `UNCERTAIN`으로 도망갈 수 있으니, **골든셋에서 UNCERTAIN 비율을
측정**하고 20%를 넘으면 프롬프트를 손본다.

> **Retriever는 관련성을 판단하지 않는다.** 점수가 낮아도 항상 K개를 채워서 넘긴다.
> 따라서 **후보에 들어왔다는 사실 자체는 관련성의 근거가 아니다.**

### 2.1 `reason` 작성 규칙 — v0.6 신설

`reason`은 **왜 그렇게 판단했는지**를 적는 칸이다. 후보 하나마다, 매핑 하나마다 붙는다.
사람이 검토 화면에서 제일 먼저 읽는 것이 이 문장이고, 오답 분석도 여기서 시작한다.
그래서 "관련 있음" 같은 응답이 쌓이면 나중에 아무것도 못 한다.

**지켜야 할 것**

| 규칙 | 근거 |
|---|---|
| 최소 10자 | "관련 있음"(5자)류를 거른다 |
| 증적 원문을 그대로 옮기지 않는다 | 인용은 `citations`가 따로 담는다. 근거는 **판단**을 적는 칸이다 |
| 통제항목 명칭만 되풀이하지 않는다 | "사용자 계정 관리"는 이유가 아니다 |
| 적정/미흡 판정을 쓰지 않는다 | Phase 1의 일이 아니다. 9.1 참고 |

**좋은 예 / 나쁜 예**

```
좋다  "계정 생성 시 관리자 승인 절차가 문서의 주제다."
좋다  "권한 검토 주기에 대한 언급이 없다."
좋다  "관련 있어 보이나 원문 근거가 불충분하다."        ← UNCERTAIN 설명

나쁘다 "관련 있음"                                    → E506 (10자 미만)
나쁘다 "사용자 계정은 관리자 승인 후 생성한다."          → E507 (원문 복붙)
나쁘다 "사용자 계정 관리"                              → E507 (명칭 반복)
나쁘다 "해당 통제항목을 적정하게 이행하고 있다."          → E505 (적정성 판정)
```

**E506·E507은 검토로 보내지 않는다.**

근거가 부실한 것은 결과가 틀린 것과 다르다. 이걸로 사람을 부르면 검토량만 늘고
정확도는 안 오른다. `validation.warnings`에 쌓아 두고 **프롬프트를 고칠 자료로 쓴다.**
`validation.passed`도 깨지 않는다.

`E505`는 다르다. 아직 검증되지 않은 판정이 결과에 섞여 그대로 보고서로 넘어가므로
**무조건 검토**(`R102`)로 보낸다.

> 최소 길이 10자는 임시값이다. 실제 응답을 보고 조정한다.
> 긴 쪽은 재지 않는다. 길다고 틀린 것이 아니다.

### 2.2 `llm_confidence` 정의 — v0.7 확정

**이것은 판단팀이 정할 값이다.** 프롬프트 작성자가 알아서 정할 수 없다.
검토 전환 임계값 `low_confidence`가 이 정의 위에 서 있기 때문이다.

지금까지는 "0~1 사이의 모델 자기확신"이라고만 했다. 그러면 모델은 아무 숫자나 낸다.
임계값 0.70이 높은 건지 낮은 건지 아무도 설명할 수 없다.

**정의**

> `llm_confidence`는 **이 판단이 원문 근거로 뒷받침되는 정도**다.
> 정답 확률도, 정확도도 아니다.

**구간**

| 값 | 상태 |
|---|---|
| **0.90 ~ 1.00** | 원문에 대상 활동이 **명시적으로** 기술돼 있다. 인용할 문장이 분명하고, 달리 읽힐 여지가 거의 없다 |
| **0.70 ~ 0.89** | 관련은 분명하나 근거가 한 군데뿐이거나 표현이 간접적이다 |
| **0.50 ~ 0.69** | 관련 가능성은 있으나 **다른 통제항목으로도 읽힌다** |
| **0.50 미만** | 근거가 약하다. 이 경우 `decision`을 `UNCERTAIN`으로 두는 쪽을 먼저 검토한다 |

**그래서 0.70이 경계다.** 그 아래는 "다른 통제항목으로도 읽히는" 구간이므로 사람이 본다.
숫자가 먼저 있고 뜻을 나중에 붙인 게 아니라, **구간을 나누고 나서 경계를 고른 것이다.**

**`NOT_RELATED`에도 매긴다**

"관련 없다"는 것도 판단이다. `NOT_RELATED` + `0.95`는 "확실히 무관",
`NOT_RELATED` + `0.55`는 "무관해 보이지만 자신 없음"이다.

> 검토 전환(`R201`)은 **`mapped_controls`의 값만** 본다.
> `NOT_RELATED`의 낮은 confidence는 검토로 보내지 않는다.
> 대신 오답 분석에 쓴다. 미탐이 어디서 나는지는 여기서 보인다.

**주의 — 이 값으로 순위를 매기지 않는다**

`llm_confidence`가 가장 높다는 이유로 PRIMARY를 정하지 않는다.
PRIMARY는 **문서의 목적**으로 정한다(4.2). 모델이 자기 확신이 센 것과
그 통제항목이 문서의 주제인 것은 다른 얘기다.

> 구간 값은 **임시다.** 실제 응답 분포를 보고 조정한다.
> 다만 **"무엇이 그 값을 만드는가"라는 문장은 바꾸지 않는다.** 그게 정의다.

## 3. `control_id` 표기 규칙 — 확정

KB 파일(`controls.json`)을 확인한 결과다.

| 항목 | 값 |
|---|---|
| 개수 | 101개 |
| 타입 | 문자열 |
| 형식 | `x.y.z` 3단계 (101개 전부 동일) |
| 끝 점 | **없음** (`2.5.1`이지 `2.5.1.`이 아니다) |
| 앞자리 0 | **없음** (`2.10.1`이지 `2.010.1`이 아니다) |
| 중복 | 없음 |
| `control_name` | 101개 전부 유일, 앞뒤 공백 없음 |

### 규칙

> `control_id`는 `controls.json`의 값을 **그대로** 쓴다.
> Validator는 정규화 없이 정확히 비교한다.
> LLM이 `2.5.1.`처럼 변형하거나 공백을 붙이면 `E301` 오류로 처리한다.

관대하게 맞춰주지 않는다. 표기를 보정하기 시작하면 **진짜 오류를 놓친다.**

`control_name`이 유일하므로 **ID ↔ 이름 일치 검사**(`E303`)를 그대로 적용할 수 있다.

### 주의 — 정렬

문자열로 정렬하면 순서가 뒤집힌다.

```
문자열 정렬:  2.1.1  2.10.1  2.11.1  2.12.1  2.2.1 ...
숫자 정렬:    2.1.1  2.2.1   ...     2.10.1  2.11.1  2.12.1
```

KB 파일 자체는 숫자 순으로 정렬돼 있다. 하지만 DB에서 `ORDER BY control_id`를 하거나
화면에서 정렬하면 `2.10`이 `2.2`보다 앞으로 온다.
**판단 파트는 정렬하지 않으므로 영향이 없지만, 결과 화면·대시보드 담당은 알아야 한다.**

## 4. 1:N 매핑

### 4.1 왜 1:N인가

증적 하나가 통제항목 하나에만 걸린다는 보장이 없다.
계정관리 지침서에는 계정 생성·삭제 절차(`2.5.1`)와
관리자 권한 승인 절차(`2.5.5`)가 같이 들어 있다.

그래서 **Multi-label 분류**로 본다. 후보 중 여러 개를 고를 수 있다.

> **방향 주의.** 여기서 1:N은 **증적 1개 → 통제항목 N개**다.
> "통제항목 1개를 증적 여러 개로 입증하는 것"은 Phase 2와 대시보드의 영역이다.

### 4.2 PRIMARY / RELATED

| 값 | 정의 |
|---|---|
| `PRIMARY` | 증적의 **주된 목적**이 이 통제항목이다. 문서가 존재하는 이유 |
| `RELATED` | 증적의 **일부 내용**이 이 통제항목과 직접 관련된다 |

판단 기준은 **문서 전체에서 차지하는 비중과 목적**이다.

- 문서 제목과 전체 구조가 무엇을 다루는가
- 그 통제항목 내용이 문서의 중심인가, 곁가지인가

`retrieval_similarity`가 가장 높다는 이유로 PRIMARY를 정하지 않는다.
검색 점수는 표현이 닮은 정도일 뿐, 문서의 목적을 모른다.

### 4.3 개수 규칙

| 규칙 | 값 |
|---|---|
| `MATCHED`일 때 `PRIMARY` | **정확히 1개** |
| `MATCHED`일 때 `RELATED` | 0개 이상 |
| `MATCHED`일 때 `mapped_controls` | 1개 이상 |
| `NO_MATCH`일 때 `mapped_controls` | **빈 배열** |
| `mapped_controls` 전체 상한 | **3개** (PRIMARY 1 + RELATED 2) |
| 동일 `control_id` 중복 | 금지 |
| 매핑된 항목의 Citation | 각각 1개 이상 필수 |
| 후보 밖 `control_id` 생성 | 금지 |

**PRIMARY가 왜 정확히 1개인가**

- **0개를 허용하면** "관련은 있는데 뭐가 주인지 모르겠다"는 결과가 쌓인다.
  Phase 2가 무엇부터 검사할지 정할 수 없다.
- **2개 이상을 허용하면** 모델이 고민을 회피한다. 애매하면 둘 다 PRIMARY로 찍는다.

하나를 반드시 고르게 하고, **고르기 어려우면 사람에게 넘긴다.**

**상한이 왜 3개인가**

임시값이다. 현재 Top-K 기본값이 5이므로 **5개 중 최대 3개**다.
증적 하나가 통제항목 4개 이상과 직접 관련되는 경우는 드물고,
그렇게 나오면 대개 모델이 확신 없이 다 긁어온 것이다.

**상한과 Top-K는 다른 숫자다.**

```
Top-K     Retriever가 넘기는 후보 개수     (그물)
상한      LLM이 최종으로 고르는 개수       (건진 것)
관계      상한 ≤ Top-K
```

골든셋의 정답 개수 분포를 보고 조정한다. 정답이 4개 이상인 사례가 있으면 올린다.
**검색팀이 Top-K를 3으로 바꾸면 상한 3은 아무 제약도 되지 않으므로 다시 검토한다.**

### 4.4 판정 절차

LLM은 이 순서를 따른다. 프롬프트에 이 순서를 그대로 넣는다.

```
1. 후보 전부에 대해 RELATED / NOT_RELATED / UNCERTAIN을 매긴다
       ↓
2. RELATED가 0개  →  match_status = NO_MATCH, mapped_controls = []
       ↓
3. RELATED가 1개  →  그것이 PRIMARY
       ↓
4. RELATED가 2개 이상
       →  그중 증적의 주된 목적에 해당하는 하나를 PRIMARY
       →  나머지는 RELATED
```

**2단계에서 주의할 것**

`NOT_RELATED`가 전부라고 해서 검색이 실패한 게 아니다.
Retriever는 관련이 없어도 항상 K개를 채워서 준다.
무관한 증적이면 후보 5개 전부 `NOT_RELATED`가 나오는 게 정상이다.

**`UNCERTAIN`만 남았을 때 — v0.6 확정**

`RELATED`가 0개인데 `UNCERTAIN`이 섞여 있으면, 그것은 "관련 없다"가 아니라
**"판단을 못 했다"**이다. 뜻이 다르다.

```
후보 5개 전부 NOT_RELATED           →  정말 관련 통제항목이 없다
NOT_RELATED 3 + UNCERTAIN 2         →  판단을 못 했다
```

**`match_status`에는 값을 추가하지 않는다. 둘 다 `NO_MATCH`다.**

`match_status`에 `UNCERTAIN`을 넣으면 Phase 2, 검토 화면, DB가 전부 바뀐다.
얻는 것에 비해 비용이 크다. 대신 **이미 있는 두 필드로 구분한다.**

| | `match_status` | 검토 사유 | 사람에게 |
|---|---|---|---|
| 정말 무관 | `NO_MATCH` | `R204`(조건부) | 간다 (초기에는) |
| 판단 보류 | `NO_MATCH` | **`R107`(무조건)** | 반드시 간다 |

`UNCERTAIN`이 하나라도 있으면 `R107`이 붙으므로, 임계값을 어떻게 조정해도
보류 건은 항상 사람에게 간다. 화면에서는 `R107`이 있으면
"판단 보류"로 표시한다. `NO_MATCH`를 그대로 보여주면 검토자가 오해한다.

**평가할 때는 반드시 나눠서 센다**

이걸 안 하면 "판단 못 한 것"이 "관련 없다고 맞힌 것"으로 집계되어
`no_match_accuracy`가 실제보다 높게 나온다. `src/metrics.py`가 네 숫자를 같이 낸다.

```
NO_MATCH 정확도          값 기준 (지금까지 쓰던 것)
 └ 판단 보류 제외         UNCERTAIN 없이 맞힌 것만        ← 진짜 실력
UNCERTAIN 비율           후보 하나라도 보류한 건의 비율
보류형 NO_MATCH          NO_MATCH 중 실은 "판단 못 함"인 비율
```

골든셋 29건 기준 현재값: `UNCERTAIN` 비율 11.1%, 보류형 `NO_MATCH` 30.0%.
**`UNCERTAIN` 비율이 20%를 넘으면 모델이 도망치고 있는 것이다.** 프롬프트를 손본다.

**4단계에서 PRIMARY를 못 고르겠으면 — v0.7에서 바꿨다**

> **바뀐 점.** v0.6까지는 "경쟁하는 후보들을 `UNCERTAIN`으로 두고 사람에게 보낸다"였다.
> **그렇게 하지 않는다.** 아래 이유로 규칙을 뒤집었다.

`RELATED` 후보를 `UNCERTAIN`으로 **내리지 않는다.** 두 가지가 망가지기 때문이다.

```
RELATED 3개 중 2개가 경쟁
  → 경쟁하는 둘을 UNCERTAIN으로 내림
  → 남은 하나(제일 관련 약한 것)가 PRIMARY가 된다     ← 뒤집힌다

RELATED 2개가 경쟁
  → 둘 다 UNCERTAIN으로 내림
  → RELATED 0개 → NO_MATCH                          ← 판단이 사라진다
```

두 번째가 특히 나쁘다. 관련 통제항목이 분명히 둘이나 있는데 결과는 "관련 없음"이 된다.
`R107`이 붙어서 사람에게 가긴 하지만, **검토 화면에 볼 것이 없다.**
사람은 모델이 뭘 놓쳤는지가 아니라 빈 결과를 받는다.

**대신 이렇게 한다.**

```
1. RELATED 판단은 그대로 둔다
2. 문서 제목·heading·앞부분에 가장 가까운 후보를 PRIMARY로 정한다
3. 그 후보의 llm_confidence를 실제 확신 수준대로 낮게 매긴다
4. reason에 "주된 목적 판단이 어려움"을 명시한다
```

3번이 자동으로 검토를 부른다. `llm_confidence`가 `low_confidence`(0.70) 아래면
`R201`이 붙고, 1:N이면 `R205`도 붙는다. **이미 있는 장치로 사람에게 간다.**

> 원칙 — **모델은 판단을 남기고, 사람이 고친다.**
> 판단을 지우면 사람이 고칠 대상이 없어지고, 모델이 뭘 어려워했는지도 기록되지 않는다.
> 판단을 남기면 그것이 오답이어도 골든셋 재료가 된다.

`UNCERTAIN`은 **원문 근거 자체가 부족할 때** 쓴다.
근거는 충분한데 둘 중 뭐가 주인지 애매한 것은 `UNCERTAIN`이 아니다.

**상한을 넘으면 — 자르지 않는다**

`RELATED`가 4개 이상 나와도 **시스템이 임의로 3개만 남기지 않는다.**
점수 순으로 자르면 잘린 것이 정답일 수 있다.

```
mapped_controls를 그대로 두고
→ E502 오류 기록
→ Human Review로 전달 (R203)
```

사람이 보고 줄이거나, 상한이 틀렸다는 근거로 쓴다.

### 4.5 NO_MATCH 허용

허용한다. Retriever는 항상 Top-K를 채워서 돌려주기 때문에,
관련 없는 증적에도 후보가 붙는다. 여기서 억지로 하나를 고르게 하면 오탐이 그대로 쌓인다.

단, 초기에는 `NO_MATCH`도 Human Review로 보낸다(`R204`).
검색이 잘못됐는지 판단이 잘못됐는지 구분해야 하기 때문이다. 정확도가 안정되면 끈다.

### 4.6 예시

### 4.8 후보 목록의 요건 — v0.7 신설

판단은 **후보 하나마다 판단 하나**라는 1:1 대응 위에 서 있다.
그래서 들어오는 후보 목록이 아래를 만족해야 한다.

| 요건 | 어기면 |
|---|---|
| 같은 `control_id`가 두 번 있으면 안 된다 | `E003` — 입력 단계에서 거부 |
| 후보가 최소 1개는 있어야 한다 | `E002` — 판단 불가 |

**중복은 실제로 잘 생긴다.**

검색이 **청크 단위**이기 때문이다. 증적 하나에 청크가 N개면 Top-5 × N개의 결과가 나오고,
같은 통제항목이 여러 청크에서 잡힌다. 그걸 증적 단위로 합칠 때 중복을 없애야 한다.

```
청크 3개 × Top-5 = 결과 15개
  → 2.5.1이 3번, 2.5.6이 2번 …
  → 증적 단위로 합치면서 중복 제거 → 후보 5개
```

**조용히 지우지 않는다.** 중복이 들어오면 입력 단계에서 막고 오류로 남긴다.
안 그러면 LLM이 같은 통제항목을 두 번 판단하고, 두 판단이 서로 다를 때
어느 쪽이 맞는지 알 방법이 없다.

> **아직 안 정해진 것 — 누가 합치는가.**
> 검색팀이 합쳐서 주는 게 자연스럽지만 확정되지 않았다.
> 우리가 합치게 되면 규칙도 우리가 정해야 한다
> (같은 `control_id`가 여러 청크에서 나오면 **가장 높은 점수를 남기고**,
> `source_chunk_ids`에 나온 청크를 전부 기록한다).

## 5. Citation 규칙

| 규칙 | 내용 |
|---|---|
| `quote` | 청크 원문 그대로. 요약·의역 금지 |
| 대조 대상 | **청크의 `text` 필드**. 원본 파일이 아니다 |
| 대조 방식 | 연속 공백을 하나로 압축한 뒤 포함 여부 검사. 유사도 비교는 쓰지 않는다 |
| `chunk_id` | 해당 증적의 입력 청크에 존재해야 한다 |
| 페이지 | **`page_start` ≤ `citation.page` ≤ `page_end`** |

### 페이지를 범위로 검사하는 이유

전처리팀 청크는 페이지 하나가 아니라 `page_start` / `page_end` 범위를 갖는다.
PDF에서 한 청크가 두 페이지에 걸칠 수 있기 때문이다.

그리고 **`page`의 의미는 파일 종류마다 다르다.**

| `file_type` | `page`의 의미 |
|---|---|
| pdf | 페이지 번호 |
| xlsx | 시트 번호 |
| pptx | 슬라이드 번호 |
| docx, txt, csv | `null` |

화면에 "3페이지"로 표시하면 XLSX에서는 틀린 말이 된다. `file_type`을 같이 봐야 한다.

### 표 청크의 원문

표는 파서가 줄마다 머리글을 붙여 문자열로 바꾼다(`table_chunker.py`).

| 표 모양 | 변환 결과 |
|---|---|
| 머리글 있는 보통 표 | `계정: user01 \| 승인자: 홍길동 \| 승인일: 2026-09-01` |
| 2칸 항목표 (신청서·서약서) | `성명: 홍길동` / `소속: 정보보호부` (줄마다 하나) |
| 한 줄짜리 표 | 칸을 ` \| `로 이음 |

구분자는 ` | `(앞뒤 공백 포함), 머리글과 값 사이는 `: `다.
빈 칸과 병합 셀은 건너뛴다. 셀 안의 줄바꿈과 연속 공백은 공백 하나로 압축된다.
표 청크 안에서 줄과 줄은 `\n`으로 이어진다.

**이 재구성된 문자열이 "원문"이다.** LLM도 이것을 보고, Validator도 이것과 대조한다.
원본 셀 구조로 되돌려 비교하지 않는다.

**인용 허용 범위**

| 인용 | 통과 여부 | 이유 |
|---|---|---|
| `점검번호: SV-001 \| 결과: 양호` | 통과 | 청크 text에 그대로 있다 |
| `점검번호: SV-001` | 통과 | 부분 문자열이다 |
| 여러 줄을 한꺼번에 인용 | 통과 | 정규화로 `\n`이 공백이 되어 포함 검사를 지난다 |
| `SV-001은 양호` | **실패** | 재구성한 문장이다. 원문에 없다 |
| `점검번호:SV-001` (공백 없음) | **실패** | 정규화는 연속 공백만 압축한다. 구분자를 지우지 않는다 |

**PDF 페이지 넘김 표 주의 — PDF에서만**

한 표가 두 페이지에 걸치면 뒷장 조각에는 머리글이 없다.
`fill_continued_headers()`가 **앞 페이지의 머리글을 뒷장 청크에 붙여준다.**
이 처리는 **PDF에만 적용된다.** XLSX·PPTX는 페이지가 바뀌면 청크를 끊으므로 해당하지 않는다.

그래서 뒷장 청크의 `text`에는 그 페이지에 실제로 인쇄되지 않은 머리글이 들어 있다.
Validator는 청크 `text` 기준이므로 통과하지만,
**검토 화면에서 원본 PDF를 보면 그 문장이 없어 보일 수 있다.** 검토자에게 안내가 필요하다.

## 6. 중복 판정

청크는 **인접한 것끼리 100자가 겹친다.** 다만 겹치지 않는 경우가 셋 있다.

| 겹치지 않는 경우 | 이유 |
|---|---|
| 표 청크 | 줄마다 머리글이 붙어 조각 하나로도 뜻이 통한다 |
| **페이지·시트·슬라이드가 바뀌는 곳** | 겹치면 인용 페이지가 틀려진다 |
| 긴 문단 하나를 나눈 경우 | 이미 겹쳐 있어 두 번 겹치지 않는다 |

**페이지 경계에서 겹치지 않는다는 점이 우리에게 중요하다.**
인용의 `page`가 실제 페이지와 어긋날 일이 그만큼 줄어든다.
다만 같은 페이지 안에서는 여전히 겹치므로, 아래 판정은 그대로 필요하다.

| 상황 | 처리 |
|---|---|
| 같은 `control_id`가 두 번 | `E304` 오류 → 검토 |
| `chunk_id`는 다른데 `quote`가 같음 | **같은 근거로 본다.** 하나만 남긴다 |
| `chunk_id`도 `quote`도 다름 | 별개 근거. 둘 다 남긴다 |

겹침 구간의 인용을 별개로 세면 **근거가 2개인 것처럼 보인다.**
실제로는 같은 문장 하나다.

## 7. 점수 필드는 절대 섞지 않는다

| 필드 | 누가 만드나 | 의미 |
|---|---|---|
| `retrieval_similarity` | 검색팀 | 벡터 유사도. 표현이 얼마나 닮았는가 |
| `llm_confidence` | LLM | 모델이 자기 판단에 매긴 값 |
| `validation.passed` | Validator | 형식·근거 검증 통과 여부 |
| `human_review.required` | Review Policy | 사람이 봐야 하는가 |

> `llm_confidence = 0.91`은 **정확도 91%가 아니다.**
> 실제 정확도는 골든셋 평가로만 계산한다. 화면에도 "정확도"라고 쓰지 않는다.

하나의 `confidence` 필드로 합치자는 얘기가 나오면 반대한다.
합치는 순간 어디서 잘못됐는지 추적할 수 없다.

### 점수의 실제 분포 — 중요

검색팀 ChromaDB는 `similarity_score = 1 - cosine_distance`, 즉 코사인 유사도 그 자체를 준다.
이론상 `-1 ~ 1`이지만 **BGE-M3 한국어 문장에서는 0.5 근처에 몰린다.**

실측 (질의: "퇴사자의 사용자 계정을 삭제하고 승인자와 처리 일자를 계정 관리대장에 기록했다")

| 순위 | 통제항목 | 점수 |
|---|---|---|
| 1 | 2.5.1 사용자 계정 관리 | 0.5833 |
| 2 | 2.5.6 접근권한 검토 | 0.5280 |
| 3 | 2.5.2 사용자 식별 | 0.5253 |
| 4 | 2.5.5 특수 계정 및 권한 관리 | 0.5089 |
| 5 | **2.9.3 백업 및 복구관리** | **0.4988** |

**계정 삭제 질의에 "백업 및 복구관리"가 0.4988로 들어온다.** 완전히 무관한데도
정답과의 차이가 0.08밖에 안 된다.

여기서 나오는 결론은 하나다.

> **점수의 절대값으로 관련성을 판단할 수 없다.**
> 0.5가 넘는다고 관련 있는 것이 아니다. 판단은 LLM이 원문을 읽고 한다.

임계값도 이 분포에 맞춰 다시 잡았다.

| 조건 | v0.3 | v0.4 | 이유 |
|---|---|---|---|
| `R202` 1·2위 점수 차 | 0.05 | **0.03** | 실측 1·2위 차가 0.055다. 0.05면 거의 모든 결과가 검토로 간다 |
| `R206` 높은 검색 점수 | 0.85 | **0.55** | 0.85는 나오지 않는다. 영영 발동하지 않는 조건이었다 |

**둘 다 여전히 임시값이다.** 골든셋 28건을 돌려서 확정한다.

| 후보가 빈 배열 | `E002` |
| 후보에 같은 `control_id`가 두 번 | `E003` |
| 그 밖의 입력 계약 위반 | `E004` |

전부 **LLM을 부르기 전에** 걸린다. 부를 이유가 없다.

**그래도 결과 객체는 반드시 만든다.**

```
processing_status = FAILED
match_status      = NO_MATCH      ← "관련 없음"이 아니라 "판단 못 함"
mapped_controls   = []
human_review      = R110 (무조건 검토)
```

> **왜 결과를 만드는가.**
> 안 만들면 그 증적은 **화면에서 사라지고 통계에서도 빠진다.**
> 사용자는 올린 파일이 어디 갔는지 알 수 없고, "처리율 100%"가 찍힌다.
> 판단 못 한 것은 판단 못 했다고 남겨야 한다.

**구현 주의** — 청크가 0개면 `MappingInput`을 **만들 수조차 없다**(`chunks`는 1개 이상 필수).
그래서 `build_result()`를 부를 수 없다. 이 경우를 위한 별도 진입점이 있다.

```python
try:
    mapping_input = MappingInput.model_validate(payload)
except ValidationError as exc:
    result = build_unjudgeable_result(
        evidence_id, version, versions,
        code=ErrorCode.INPUT_NO_CHUNKS, message=str(exc),
    )
else:
    result = build_result(raw_response, mapping_input, versions)
```

프롬프트 쪽에서도 같은 조건을 잡는다(`PromptInputError`).
**그때 예외를 그대로 위로 던지지 말고 위 경로로 결과를 만들어야 한다.**

### 8.2 파서 오류

파싱 실패나 빈 문서일 때 전처리팀은 청크를 `[]`로 준다.
그러면 8.1의 `E001` 경로를 탄다.

평가 지표를 계산할 때 `FAILED`는 분모에 포함하되
`processing_status`로 구분해서 따로 센다(`invalid_output_rate`).

### 8.3 LLM 호출 실패

`error_codes_v0.1.md` 참고. 재시도는 1회, Timeout 60초다.

### 9.1 적정성 판정 감지 (`E505`) — v0.6 구현

Phase 1은 **증적과 통제항목을 연결하는 것까지만** 한다.
"이 증적이 통제를 충족하는가"는 Phase 2의 일이고, 근거도 절차도 다르다.
모델이 Phase 1에서 합격·불합격을 내버리면 **검증되지 않은 판정이 결과에 섞여
그대로 보고서로 넘어간다.** 인증 심사 도구에서 이건 가장 위험한 실수다.

**어디를 보는가 — `reason`만 본다**

`quote`는 검사하지 않는다. 인용문은 증적 원문 그대로이고, 증적에는
"미흡", "위반", "부적합"이 얼마든지 나온다. 점검 결과 보고서 자체가 증적일 수도 있다.
**원문에 있는 단어로 모델을 탓하면 안 된다.**

**무엇을 잡는가**

| 구분 | 표현 | 조건 |
|---|---|---|
| 판정 어휘 | 적정·부적정, 적합·부적합, 위반, 결함, 미준수, 미이행, 보완/조치/개선 필요 | 무조건 |
| 대상이 통제일 때만 | 충족·미충족, 미흡, 불충분 | **앞쪽에 "통제항목·인증기준·요구사항"이 있을 때만** |

두 번째 줄이 중요하다. `UNCERTAIN`의 표준 설명이 **"관련 있어 보이나 원문 근거가
불충분하다"**인데, `불충분`을 무조건 잡으면 정상 응답이 전부 걸린다.
"근거가 불충분하다"는 판정이 아니라 **보류 사유**다.

```
잡는다     "통제항목 요구사항을 충족하지 않는다."
잡는다     "비밀번호 정책을 준수하지 않고 있다."
안 잡는다  "관련 있어 보이나 원문 근거가 불충분하다."
안 잡는다  "약어만 있어 판단 근거가 미흡하다."
```

> 표현 목록은 **임시값이다.** 실제 LLM 응답을 보고 조정한다.
> 오탐이 나도 결과를 버리지 않는다. 사람에게 한 번 보여줄 뿐이다.
> 코드는 `src/validators.py`의 `detect_adequacy_judgment()`.

## 12. 입력팀 규격과의 접점

### 12.1 `evidence_id` 표기 — **전처리팀 내부에서 어긋나 있다**

| 출처 | `evidence_id` | `chunk_id` |
|---|---|---|
| `database/config.py` (`ID_PREFIX="E"`, `ID_DIGITS=4`) | `"E0001"` 문자열 | — |
| JSON 규격 문서 ⑤ 본문 | `"E0001"` | `E0001_v1_c0003` |
| JSON 규격 문서 요약 | `"000001"` | `000001_v1_c0003` |
| **`chunk_format.py` 실제 코드** | **정수 `1`** | `000001_v1_c0003` |

`make_chunk_id("E0001", 1, 3)`을 호출하면 `ValueError`가 난다.
코드가 `_is_pos_int`로 정수만 받기 때문이다.
**DB가 문자열 `E0001`을 발급하는데 청킹 모듈이 그것을 받지 못하는 상태다.**

> **전처리팀에 물어볼 것**
> `evidence_id`를 `E0001`로 확정하고 `chunk_format.py`를 고칠지,
> 아니면 `000001`(정수)로 가고 `database/config.py`의 `ID_PREFIX`를 뺄지.

### 12.2 우리 쪽 처리 — 표기를 고정하지 않는다

`evidence_id`는 **문자열로 받는다.** JSON 규격 문서의 지적대로,
숫자로 저장하면 앞의 0이 사라져 DB와 대조가 안 된다.

표기 자체는 검사하지 않고, **관계만 검사한다.**

```
chunk_id == f"{evidence_id}_v{version}_c{chunk_index:04d}"
```

`E0001`이든 `000001`이든 이 관계는 변하지 않는다.
어느 쪽으로 정해져도 우리 코드는 그대로 돌아가고,
**어긋난 조합은 그대로 잡힌다.**

한 증적의 입력에 다른 증적·버전의 청크가 섞이면 입력 단계에서 막는다.

### 12.3 `evidence.status`로 옮기는 규칙

입력팀 DB의 `evidence.status`는 8개 값을 쓰는데,
**처리 상태와 검토 상태가 한 칸에 섞여 있다**(`REVIEW_REQUIRED`).

우리는 둘을 나눠 관리하고, 백엔드에 넘기는 순간에만 합친다.

| 판단 결과 | `evidence.status` |
|---|---|
| `processing_status = FAILED` | `FAILED` |
| `human_review.required = true` | `REVIEW_REQUIRED` |
| 그 외 | `COMPLETED` |

**거꾸로는 복원할 수 없다.** `evidence.status`만 보고 판단 결과를 되살리면 안 된다.
검토 사유와 오류코드는 `Phase1MappingResult`에만 있다.

### 12.4 파서 오류는 청크 `[]`로 온다

파서는 예외를 던지지 않고 `errors`에 코드를 넣는다. 코드는 두 가지뿐이다.

| 코드 | 언제 |
|---|---|
| `corrupted_file` | 파일을 열 수 없음 |
| `empty_document` | 열리는데 뽑을 내용이 없음 (스캔본 포함) |

이 경우 청크는 `[]`가 되고, 우리는 8장대로 `processing_status = FAILED`로 처리한다.

> 스캔본과 진짜 빈 문서가 지금은 둘 다 `empty_document`라 구분되지 않는다.
> 입력팀이 `no_text_layer` 코드 추가를 논의 중이다.
> **추가되면 OCR 대상과 판독 불가 문서를 구분할 수 있다.**

### 12.5 OCR 표시가 아직 없다 — `R207`이 발동하지 않을 수 있다

청크의 `source`는 `parser` / `ocr` 두 값인데,
**파서 블록에는 `source` 칸이 아직 없다.** 넣으려면 파서 6종을 전부 고쳐야 한다고
입력팀이 미결정으로 남겨 뒀다.

그래서 현재는 모든 청크가 `source = "parser"`로 올 가능성이 높다.
그러면 검토 조건 `R207`(OCR 청크 인용 시 검토)은 **한 번도 발동하지 않는다.**

> **전처리팀에 물어볼 것**
> OCR을 붙일 때 청크의 `source`를 `"ocr"`로 채워줄 수 있는지.
> 안 되면 `R207`을 빼거나 다른 신호를 써야 한다.

### 12.6 API 오류코드와 섞지 않는다

입력팀 API는 공통 봉투 `{success, data, error:{code, message}}`를 쓰고,
`INVALID_EXTENSION` 같은 자체 코드를 갖는다.

**우리 오류코드(E0xx~E5xx)와는 별개다.**
판단 파트의 오류는 `validation.issues`에 들어가고,
API 봉투의 `error`는 요청 자체가 실패했을 때만 채워진다.

## 13. 프롬프트에 그대로 넣을 문구 — v0.7 신설

프롬프트를 쓰는 사람이 규칙 문서를 해석해서 옮겨 적으면, **문서와 프롬프트가 갈라진다.**
그래서 판단팀이 문장까지 정해서 넘긴다. 아래는 복사해서 System Prompt에 붙이면 된다.

각 항목이 어느 규칙에서 나왔는지는 괄호로 표시했다.

### 13.1 `llm_confidence` 매기는 법 (→ 2.2)

```
llm_confidence는 이 판단이 원문 근거로 뒷받침되는 정도다.
정답 확률도, 정확도도 아니다.

0.90 ~ 1.00
  원문에 대상 활동이 명시적으로 기술되어 있다.
  인용할 문장이 분명하고 달리 읽힐 여지가 거의 없다.

0.70 ~ 0.89
  관련은 분명하나 근거가 한 군데뿐이거나 표현이 간접적이다.

0.50 ~ 0.69
  관련 가능성은 있으나 다른 통제항목으로도 읽힌다.

0.50 미만
  근거가 약하다. decision을 UNCERTAIN으로 두는 쪽을 먼저 검토한다.

NOT_RELATED에도 llm_confidence를 매긴다.
"관련 없다"는 판단에 대한 확신도다.

llm_confidence가 가장 높다는 이유로 PRIMARY를 정하지 않는다.
PRIMARY는 문서의 주된 목적으로 정한다.
```

### 13.2 `reason` 쓰는 법 (→ 2.1)

```
reason은 왜 그렇게 판단했는지를 쓰는 칸이다.

- 최소 10자 이상으로 쓴다.
- 증적 원문을 그대로 복사해 붙이지 않는다. 인용은 citations가 담당한다.
- 통제항목 명칭만 되풀이하지 않는다.
- 적정/미흡/충족/미충족/위반/준수 같은 판정 표현을 쓰지 않는다.
  Phase 1은 증적과 통제항목을 연결하는 것까지만 한다.

좋은 예
  "계정 생성 시 관리자 승인 절차가 문서의 주제다."
  "권한 검토 주기에 대한 언급이 없다."
  "관련 있어 보이나 원문 근거가 불충분하다."

나쁜 예
  "관련 있음"                              (너무 짧다)
  "사용자 계정은 관리자 승인 후 생성한다."    (원문 복사)
  "사용자 계정 관리"                        (명칭 반복)
  "해당 통제항목을 적정하게 이행하고 있다."   (판정)
```

### 13.3 PRIMARY를 고르기 어려울 때 (→ 4.4)

```
PRIMARY를 근거 있게 고를 수 없어도 RELATED 판단을 UNCERTAIN으로 내리지 않는다.
판단을 지우면 사람이 검토할 대상이 사라진다.

대신 아래 순서를 따른다.

1. RELATED 판단은 그대로 둔다.
2. 문서 제목, heading, 앞부분 청크에 가장 가까운 후보를 PRIMARY로 정한다.
3. 그 후보의 llm_confidence를 실제 확신 수준대로 낮게 매긴다.
4. reason에 주된 목적 판단이 어려웠다는 점을 적는다.

UNCERTAIN은 원문 근거 자체가 부족할 때 쓴다.
근거는 충분한데 둘 중 무엇이 주된 목적인지 애매한 경우는 UNCERTAIN이 아니다.
```

### 13.4 호출부에서 처리할 것 (→ 8.1)

프롬프트 문구가 아니라 **코드** 얘기다.

```python
# 청크 0개, 후보 0개, 후보 중복은 LLM을 부르기 전에 걸린다.
# 예외를 위로 던지지 말고 결과 객체를 만든다.
# 안 그러면 그 증적이 화면에서 사라진다.

try:
    pkg = build_prompt_package(...)
except PromptInputError as exc:
    result = build_unjudgeable_result(
        evidence_id, version, versions,
        code=ErrorCode.INPUT_NO_CHUNKS,   # 상황에 맞는 E00x
        message=str(exc),
    )
else:
    raw = call_llm(...)
    result = build_result(raw, mapping_input, versions)
```

`build_result()`는 **어떤 입력이 와도 예외를 던지지 않는다.**
LLM 호출이 실패했으면 `call_error=`에 오류코드를 주면 된다.

### 13.5 결과에 같이 남길 것 (→ 10)
